# 枫桦景苑统一停车与车位管理设计

> 状态：调研后的开发设计稿  
> 更新日期：2026-09-29  
> 适用范围：枫桦景苑一期停车、枫桦景苑二期停车、二期大车库、二期人防车库  
> 目标：操作员只维护一份住户和车辆资料，通过勾选为同一车牌开通或取消各停车区域权限，同时正确处理按车辆收费、按车位收费、车位产权和外部系统同步。

## 1. 核心结论

业务上应采用“一份住户、一份车辆档案、四个独立授权目标”的模型。底层虽然是三个系统，但页面不能要求操作员理解数据库、控制器或德立云接口。

```text
枫桦景苑住户
└─ 车辆：沪A12345
   ├─ 枫桦景苑一期停车
   ├─ 枫桦景苑二期停车
   ├─ 枫桦景苑二期大车库
   └─ 枫桦景苑二期人防车库
```

四个授权目标必须独立保存车位、收费方式、外部记录编号和同步状态。同一车牌可以同时勾选多个目标，也可以只开通或取消其中一个目标。业务上每辆车只有一个统一到期日，所有已开通停车区共用。

## 2. 已验证的现状

### 2.1 一期、二期本地停车系统

- 管理软件位于 `192.168.1.80`。
- 一期程序目录：`Program Files (x86)\停车场管合理系统\一期\停车场管理中心`。
- 二期程序目录：`Program Files (x86)\停车场管合理系统\二期\停车场管理中心`。
- 数据库服务器位于 `192.168.6.3`，开放 SQL Server 端口 1433。
- 一期数据库：`parking1`。
- 二期数据库：`parking2`。
- SQL Server 版本为 2008 R2，兼容级别 100。
- 两套 `停车场管理中心` 均为 2.3.0.0，`ser.exe` 与 `Protocol.dll` 文件一致，差异主要来自数据库配置。
- 一期当前有 2 个硬件目标，二期当前有 9 个硬件目标。
- 2026-09-29 调研快照中，有 133 个车牌同时存在于一期、二期；其中 61 个车牌两边到期日不同。物业后续确认业务上每辆车只有一个到期日，因此这 61 条是需要对账和确认主值的外部历史差异，不应固化为 PMS 的多到期日模型。

已确认可复用的存储过程：

| 业务 | 存储过程 |
|---|---|
| 新车登记 | `AddIssue` |
| 车牌续期 | `Palte_extend` |
| 修改或更换车牌 | `Up_PakIssue` |
| 注销车辆 | `Add_Del_Plate` |
| 创建设备下载任务 | `Add_DownloadCard` |
| 增加通道权限 | `Add_Release` |
| 查询设备下载任务 | `Get_Download` |

厂商 `Protocol.dll` 包含 `DownloadCarNo`、`DelCarNo`、`InitializationCar` 等导出函数，具备直接下发和删除车牌的可能性，但函数签名和控制器成功回执仍须通过受控测试确认。

旧库中的 `Car_Issue.Car_Zt` 与历史 `Car_Download` 状态存在不能简单一一对应的情况。PMS 必须维护自己的同步任务流水并逐目标确认，不能只依据一个旧状态字段宣布成功。

数据库凭据不得写入本文档、Git、前端或普通日志。

### 2.2 德立云人防车库

当前平台的“开放接口 AccessKey”页面确认存在停车管理接口，并支持按接口单独授权。旧的 `德立云智慧物联网平台-门禁对接-API开发文档-V1.0.4.pdf` 是约 2019 年的门禁文档，不是当前停车接口文档。

旧文档中的以下约定可作为待验证参考，不能直接作为当前契约：

- 基础地址曾为 `https://openapi.deliyun.cn/acs/{method}`。
- HTTPS POST。
- 公共参数曾包含 `accessKeyID`、`version`、`timestamp`、`sign`、`commKey`。
- 业务 JSON 曾放在表单字段 `data` 中，并参与 ASCII 排序和 MD5 小写签名。

当前账号实时接口清单中确认存在：

| 查询 | `findCarList` | 登记车辆列表 |
| 查询 | `findCarGroup` | 车辆分组列表 |
| 查询 | `findCarChargeRule` | 月票车缴费规则 |
| 查询 | `findPoolParkList` | 车位池车位列表 |

| 管理 | `saveCar` | 新增或修改登记车辆 |
| 管理 | `deleteCar` | 删除登记车辆 |

## 3. 系统和授权目标映射

| PMS 授权目标 | 底层系统 | 初步接入方式 | 收费主体 |
|---|---|---|---|
| `phase1_parking`（一期地面车库） | `parking1` | `P_Effective` 通道号 5/7；本地网关确认 `P_Download` 覆盖授权通道 | 车辆 |
| `phase2_parking`（二期地面车库） | `parking2` | `P_Effective` 通道号 9/11/13；本地网关确认 `P_Download` 覆盖授权通道 | 车辆 |
| `phase2_main_garage`（二期大车库） | `parking2` | `P_Effective` 通道号 15/17/19/21；本地网关确认 `P_Download` 覆盖授权通道 | 车位 |
| `phase2_civil_defense_garage` | 德立云 | 当前停车开放 API | 根据德立云实际规则配置 |

即使二期停车和二期大车库共用 `parking2`，PMS 也必须将它们作为两个独立授权目标，以便分别开通、取消、收费和对账。

`P_Effective`、`P_Download` 的字符串位置编号表示车辆进出通道号，不表示库位或车位。`parking2` 原人防通道号 23/25 已停用，查询、写入和下载验收均忽略。二期人防车库权限只以德立云是否存在该车牌为准。二期大车库是二期地面车库的子车库：仅开大车库可用于促使车辆必须停入大车库；地面和大车库同时开通时，不触发驶出地面通道的临时车计费。两个目标仍由操作员独立勾选，不做隐式联动。

## 5. 车辆与车库授权页面

### 5.1 先选住户

支持搜索：

- 房号，例如 `228/5/301`。
- 业主或住户姓名。
- 手机号。
- 车牌号。

选中后展示：

```text
228/5/301
枫桦景苑二期 · 5号楼 · 301室
住户：张某某
```

随后同时加载：

1. 该住户名下的产权或使用车位。
2. 该住户名下的全部登记车辆。
3. 车辆在四个授权目标中的实时或最近同步状态。

没有车位或车辆时显示明确空状态，不能留空白。

### 5.2 车位摘要

示例：

```text
大车库
DK23    产权车位    管理费至 2026-12-31    已绑定 沪A12345

人防车库
MF96    使用车位    月租至 2026-10-31      当前空置
```

编号规则：

- 大车库使用 `DK23` 格式。
- 人防车库使用 `MF96` 格式。
- 自动去除空格并转大写。
- 当前没有多层，不增加无意义的楼层必填字段。
- 同一车库类型内车位编号唯一。

### 5.3 真实车牌样式的车辆卡片

每辆车使用模拟真实号牌的卡片展示：

- 7 位普通车牌：蓝底白字。
- 8 位新能源车牌：绿底黑字。
- 军警、港澳等特殊号牌允许有权限的管理员手动调整类型。

车牌展示中的中点只用于视觉，不写入数据库。数据库保存去空格、去中点、转大写后的标准值。

每张车辆卡片展示：

- 车牌号和号牌类型。
- 车辆身份：业主车、亲情车、租户车、临时授权车。
- 绑定车位。
- 车辆统一到期日和四项停车授权。
- 收费项目和收费主体。
- 最后入库时间。
- 最后出库时间。
- 当前在场状态。
- 外部系统同步状态。

示例：

```text
┌──────────────────┐
│  沪 A·12345      │  蓝牌
└──────────────────┘
业主车 · 燃油车
绑定车位：DK23

车辆到期：2026-12-31
☑ 一期停车                               已同步
☑ 二期停车                               已同步
☑ 二期大车库        DK23                 已开通
☐ 二期人防车库      未开通

收费：大车库管理费
最后入库：2026-09-28 18:35
最后出库：2026-09-29 08:12
```

同一车辆跨多个车库时，卡片显示最近一次总体进出时间；展开后显示每个授权目标各自的最后入库、最后出库和当前状态。

### 5.4 授权勾选

操作员面对的是四个业务勾选项：

```text
☑ 枫桦景苑一期停车
☑ 枫桦景苑二期停车
☑ 枫桦景苑二期大车库    车位：DK23
☐ 枫桦景苑二期人防车库
```

勾选表示申请开通，取消勾选表示申请撤销对应区域授权，不表示删除车辆档案或车位产权。

每个目标允许拥有不同的车位、收费方式和同步结果，但不再维护各自的截止日期。到期日是车辆档案的统一字段。

## 6. 新车登记与提前查重

新车登记必须分成“先查车牌”和“补充资料”两个阶段，禁止填完全部资料后才提示重复。

### 6.1 第一阶段只输入车牌

输入每个字符后，对以下来源进行模糊查询：

- PMS 统一车辆档案。
- `parking1`。
- `parking2`。
- 德立云人防车库。

输入 2 至 3 个有效字符后开始查询，前端采用约 300 毫秒防抖。最终提交前仍必须由服务端执行一次完整精确查重。

匹配结果：

1. **当前住户已经登记**：打开现有车辆，可增加其他车库权限，不重复创建。
2. **其他住户已经登记**：阻止直接登记，提示核实换房、转让、换车或历史录错；敏感住户信息按权限脱敏。
3. **只有外部旧系统存在**：允许认领并合并为 PMS 车辆档案，保留外部编号和原授权。
4. **没有登记过**：才展开完整登记表单。
5. **相似车牌**：提示可能混淆的 `0/O`、`8/B`、`5/S` 等记录，防止录错。

同一车牌已经存在于一期并不表示不能开二期；查重的结果应合并到同一车辆档案，再为它增加新的授权目标。

### 6.2 鼠标车牌输入小窗

点击车牌输入框后显示专用键盘：

1. 省份简称，默认优先“沪”。
2. 第二位英文字母。
3. 后续位置允许合法字母和数字。
4. 输入至第 8 位时自动切换为新能源绿牌预览。

要求：

- 支持鼠标点击和实体键盘。
- 自动转大写。
- 提供退格和清空。
- 不提供当前位不合法的字符。
- 输入过程中实时更新蓝牌或绿牌效果。
- 完成后立即查重，无需先点下一步。

## 7. 收费模型

停车授权和收费状态必须分开。已缴费不等于控制器已开通，已开通也不代表已缴费。

### 7.1 按车辆收费

适用于月租车等：

```text
收费主体：沪A12345
收费项目：二期月租停车费
期限：2026-01-01 至 2026-12-31
```

### 7.2 按车位收费

大车库只缴管理费，收费主体是车位：

```text
收费主体：DK23
收费项目：二期大车库管理费
产权住户：228/5/301
期限：2026年度
```

更换绑定车牌时，车位管理费不应重新生成或转为车辆停车费。

收费记录至少包含：

```text
charge_subject_type: vehicle | parking_space
charge_subject_id
charge_item_code
start_at
end_at
payment_status
```

页面明确标注“按车辆收费”或“按车位收费”。欠费后是否自动撤销通行权限由物业规则配置，不能硬编码为默认行为。

## 9. 后期真实车库地图

第一版先完成列表和车位编号管理，但从首版开始预留坐标、多边形和朝向。

地图状态建议：

- 绿色：空置。
- 蓝色：已分配但当前车辆不在场。
- 红色：当前占用。
- 灰色：停用或施工。
- 黄色：状态不确定。

必须区分：

- **已分配**：车位有产权或使用住户。
- **已占用**：车位当前实际有车辆。

仅依赖出入场记录只能推测车辆是否在某个车库内，不能证明车辆实际停在 `DK23`。需要真实车位占用时，应接入车位相机、地磁、人工盘点或其他车位检测数据，并记录 `occupancy_source`。

## 11. 业务流程

### 11.1 新车登记

```text
选择住户
→ 输入车牌并跨系统模糊查重
→ 合并已有车辆或确认新建
→ 选择车辆身份
→ 勾选四项授权目标
→ 选择车位和收费项目
→ 预览变更
→ 按目标创建同步任务
→ 分别展示每个目标的结果
```

### 11.2 续期

- 每辆车只展示一个当前到期日，所有已开通停车区共用。
- 提供 1、2、3、6、12 个月快捷续期，默认从现有到期日向后顺延，不能覆盖尚未使用的剩余期限。
- 业主车和租户车使用不同计费规则；规则分别配置月单价和 12 个月年付价，年付可优惠。
- 页面提供缴费验算，按车辆类型和续期月数显示应收金额与年付节省金额。
- 按车位收费的大车库续期更新车位管理费，不因换车重复收费。

### 11.3 开通或取消车库

- 勾选表示创建授权任务。
- 取消勾选表示创建撤销任务。
- 撤销授权不删除车辆档案、住户、车位或产权关系。
- 只有外部系统确认后，状态才变为已开通或已取消。

### 11.4 换车

换车不能直接覆盖旧车牌：

```text
录入新车牌并查重
→ 读取旧车的四项授权、车位、期限和收费关系
→ 为新车牌逐目标开通
→ 确认新车授权成功
→ 逐目标撤销旧车牌
→ 旧车归档
```

默认继承原住户、车位、授权、期限和收费关系，但操作员可以取消某一项目标。出现部分失败时保留清楚的目标级状态并允许只重试失败目标。

### 11.5 亲情车和一车位多车

亲情车是独立车辆档案，归属于同一住户。系统分别管理：

- 登记车辆数量。
- 可同时在场的车位容量。

需要支持一车位多车但仅允许一辆在场、多车位多车，以及亲情车只开普通停车而不进入大车库或人防车库。

## 12. 最后入库、出库和在场状态

每个授权目标分别保存：

```text
last_entry_at
last_exit_at
current_presence: inside | outside | unknown
last_event_source
last_event_synced_at
```

车辆卡片显示所有目标中最近的一次总体进出事件，展开后显示：

| 停车区域 | 最后入库 | 最后出库 | 当前状态 |
|---|---|---|---|
| 一期停车 | 09-28 18:35 | 09-29 08:12 | 已出场 |
| 二期停车 | 09-27 17:20 | 09-28 07:50 | 已出场 |
| 二期大车库 | 09-28 18:36 | 09-29 08:10 | 已出场 |
| 二期人防车库 | — | — | 未开通 |

## 13. 同步架构

建议复用 PMS 门禁项目已有的本地代理通信、认证、任务租约和 DPAPI 密钥保护能力，在 `192.168.1.80` 增加停车网关角色：

```text
PMS 管理网页
      ↓
PMS API：住户、车辆、车位、收费、授权和任务状态
      ↓ HTTPS 出站领取任务
192.168.1.80 parking_gateway
      ├─ parking1
      ├─ parking2
      └─ Protocol.dll / 厂商控制器

PMS API
      └─ 德立云开放 API：人防车库
```

浏览器不得直接连接 SQL Server 或持有德立云 Secret。旧 SQL Server 1433 不对公网开放。

## 14. 状态和失败处理

每个授权目标独立使用状态：

```text
not_authorized
pending_enable
enabling
active
pending_disable
disabling
disabled
waiting_retry
failed
unknown
```

三个外部系统不可能组成同一个数据库事务，必须采用目标级任务和补偿流程。例如：

```text
一期停车          已开通
二期停车          已开通
二期大车库        上传失败 · 可重试
二期人防车库      已开通
```

不能因为三个成功、一个失败就把整次操作显示为成功，也不能盲目回滚已经生效的其他目标。重试只处理失败目标，所有写入任务带幂等键。

## 15. 权限、审计和安全

- 查询住户、登记车辆、换车、取消授权、调整产权、收费和查看敏感信息分别配置权限。
- 其他住户的重复车牌结果按权限脱敏。
- 每次操作记录操作人、住户、房号、车牌、目标系统、变更前后值、时间和返回结果。
- 密钥类配置只保存在服务端或本地网关的加密存储中，不回显完整值。
- AccessKey 使用最小接口授权并可单独吊销。
- 第三方失败不吞掉具体原因；页面显示目标系统、失败阶段、可执行动作和可查错误编号。

## 16. 自动对账

每天从 `parking1`、`parking2` 和德立云读取登记车辆及授权，和 PMS 比较：

- PMS 已开通、外部不存在。
- 外部存在、PMS 未登记。
- 到期日不一致。
- 车牌归属住户不一致。
- 车位绑定不一致。
- 已取消但控制器仍有权限。
- 最后进出事件长时间未同步。

差异先进入对账页面，由管理员确认“以 PMS 修复外部”或“将外部现状认领进 PMS”，不能自动覆盖未经确认的历史业务数据。

## 18. 开发前必须完成的受控验证

### 18.1 本地停车系统

使用测试车牌分别执行并记录数据库、下载队列和控制器变化：

1. 一期新增、续期、注销、换车。
2. 二期新增、续期、注销、换车。
3. 二期普通停车和大车库分别开通、取消。
4. 确认 `P_Effective`、`P_Download`、`Car_Release` 和具体设备的映射。
5. 确认控制器成功回执以及旧状态字段的真实语义。
6. 确认本地网关应复用旧下载队列还是直接调用 `Protocol.dll`。

### 18.2 德立云

使用 PMS 专用测试 AccessKey，只授权必要接口，先完成只读验证：

1. 当前 API 域名和版本。
2. 当前签名算法及参数编码。
3. `commKey` 对应的人防项目。
4. `findPunitInfo`、`findParkGarage`、`findCarList`、`findPoolParkList` 的请求和返回结构。
5. 人防车库应使用普通月票车还是车位池模式。
6. 只读验证通过后，使用测试车牌验证新增、车库授权、续期和取消。

### 18.3 业务规则

开发前由物业确认：

- 一期、二期普通停车的收费项目和续期规则。
- 大车库管理费周期、欠费后是否自动取消通行。
- 人防车库是按车辆收费还是按车位收费。
- 每户、每个车位允许登记几辆车以及允许几辆同时在场。
- 产权、长期使用、租赁车位的变更审批规则。
- 换车时各授权目标是否默认全部继承。

## 19. 验收标准

- 选中住户后能完整看到名下车位和车辆。
- 7 位车牌显示蓝牌，8 位新能源车牌显示绿牌，特殊号牌允许人工修正。
- 新车登记在展开完整表单前已经完成跨系统模糊查重。
- 已存在于一期的车牌能合并后继续增加二期或人防授权，不重复建车。
- 一个车牌可以独立勾选任意授权目标并分别显示同步状态；车辆只显示一个统一到期日。
- 大车库收费明确显示为按车位收取的管理费，换车不重复生成车位管理费。
- `DK23`、`MF96` 等车位能关联产权或使用住户并保留变更历史。
- 开通、取消、续期、换车均可看到每个目标系统的真实结果。
- 单个目标失败不掩盖为整体成功，修复后只重试失败目标。
- 最后入库、最后出库和当前在场状态按授权目标可追溯。
- 所有敏感操作有操作人、时间、变更内容和错误编号。
- 页面和日志中不出现数据库密码、AccessKey Secret 或完整内部凭据。
