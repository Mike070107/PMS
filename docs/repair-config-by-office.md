# 报修类型配置按管理处区分 + 领料仓库按管理处自动匹配

> 2026-08-26 Mike 在「报修类型配置」弹窗里提出，2026-08-27 已实现上线。下面先写做成了什么样，再保留原设计依据。

## 已实现（2026-08-27）

- **规则按管理处分套**：`repair_type_rules.office_id`（空 = 公司默认模板）。后台「报修类型配置」顶部 Tab：
  「公司默认（模板）」+ 每个管理处；管理处那页第一次打开由后端从模板复制一份（`listRepairTypeRules(user, officeId)`），之后各改各的。
- **取规则的顺序**：报修小区 → `communities.office_id`（分期跟顶层小区）→ 该管理处那套；没有就公司默认。
  自动派单、类型关键词判定、更正学词、业主端 `/repair-types?communityId=` 全走 `RepairsService.rulesForCommunity`。
- **默认维修工按范围过滤**：`/work-orders/technicians?scope=company`（只列全公司范围的人）/ `?officeId=X`（全公司 + 范围覆盖 X 的人），
  返回 `scope: 'all' | 'office'`；保存时服务端 `assertAssignee(..., officeId)` 同样校验，不合规 400 写明原因。
  「总公司维修工 / XX 管理处维修工」= 两个数据范围不同的角色，不需要新的用户类型。
- **领料仓库自动匹配**：删掉 `repair_type_warehouses` 及后台那一列。维修工「从库存选」时按工单所在小区 / 管理处匹配：
  同小区仓 → 同管理处仓（仓挂在该管理处下任一小区）→ 公司总仓（不挂小区）；匹配不到时端上提示去「库存与采购」给管理处建仓，仍可手动挑仓。
  仓库归属沿用 `warehouses.community_id`，没有新字段、没有数据迁移。

### 2026-08-27 晚追加
- 仓库档案新增「所属管理处」（`warehouses.office_id`，老小区仓按 小区 → 管理处 懒补；新增仓库类型「管理处仓」）。
- 人员 → 管理处由角色数据范围推（`AccessService.userOfficeIds` / 登录下发的 `access.offices`），
  所有按人匹配仓库的地方都走这一条：员工端「材料与库存」进页默认选本人管理处的仓（全公司范围的人保持「全部仓库」）；
  工单选料在「工单所在小区 / 管理处」都没仓时退到维修工本人管理处的仓，再退公司级。
- 员工端「材料与库存」的「待补资料」旁加了「仅显示有货」复选框（默认勾上；点「低于安全库存 / 待补资料」时自动放开）。
- 新建管理处时同步：从公司默认复制一套报修类型配置、建一个同名「管理处仓」（已有同名仓则挂到该管理处）。
  报修类型配置弹窗的管理处 Tab 改为现取 `/repair-type-rules/offices`，新建的管理处不用重新登录就出现。

### 没做 / 待观察
- 业主端小程序请求 `/repair-types` 时还没带 `communityId`，客户端预判类型用的是公司默认关键词；服务端建单时会按小区所属管理处再判一次（客户端没传类型时）。
  如果某管理处大改关键词，再让业主端带上小区 id。
- 派单弹窗的候选人没按管理处过滤（只校验能不能接单），派错管理处的人属于人工决定，先不拦。

## 结论一：不需要新的用户类型，两个角色就能区分

「物业总公司维修工」和「枫桦景苑管理处维修工」就是**同一套功能勾选、数据范围不同的两个角色**：

- 物业总公司维修工：数据范围 = 全公司；
- 枫桦景苑管理处维修工：数据范围 = 枫桦景苑管理处（自动含其下全部小区）。

这套东西 RBAC 一期已经做完，业务角色页现在就能建。系统据此判断「某维修工能不能被某管理处选为默认维修工」：
**范围覆盖该管理处（全公司，或范围里含这个管理处 / 含它下面的小区）才能选**。总公司维修工自然可以被多个管理处选；管理处维修工只会出现在自己管理处的下拉里。

## 结论二：领料仓库按「工单所在管理处」匹配，而不是按「维修工所属管理处」

Mike 原话是「根据用户所属物业管理处来匹配」。按人算有个漏洞：总公司维修工跨管理处，他没有唯一的「所属管理处」。
按**工单的小区 → 管理处**算，两类维修工都成立，而且材料本来就是从现场那个管理处的仓库领的。
对专属维修工两种算法结果一致，所以建议统一按工单所在管理处。

## 方案

### 1. 报修类型规则挂管理处
- `repair_type_rules` 加 `office_id`（可空 = **公司默认模板**），唯一键改为 (tenant_id, office_id, repair_type)。
- 后台「报修类型配置」弹窗顶部加管理处 Tab：`公司默认 | 枫桦景苑管理处 | …`。
  管理处页**首次打开从公司默认复制一份**（懒复制），之后各改各的，互不影响。
- 取规则的顺序（自动派单、类型关键词判定、「猜你想输」、默认时限一律同一函数）：
  报修小区 → `communities.office_id` → 该管理处规则；没有 → 公司默认。

### 2. 默认维修工下拉按管理处过滤
- 候选 = 勾了「工单池 · 接单」**且**数据范围覆盖该管理处的人；公司默认页 = 全公司范围的人。
- 保存时服务端同样校验，不合规 400：「王师傅是枫桦景苑管理处的维修工，不能选为吴泾管理处的默认维修工」。
- `/work-orders/technicians` 增加 `officeId` 查询参数，派单弹窗也按本单管理处过滤（顺手把派单选错人的口子堵上）。

### 3. 领料仓库自动匹配
- `warehouses` 加 `office_id`（可空 = 公司总仓）；`community_id` 由迁移回填成 `communities.office_id` 后废弃。
- **删掉** `repair_type_warehouses` 表和后台那一列「领料仓库（先选小区）」。
- 「从库存选」默认仓：本单管理处的启用仓库（多个时取第一个，允许手动切换）→ 没有则公司总仓 → 再没有才提示「请在『库存与采购』里给 XX 管理处建一个仓库」。
- 员工端小程序只改提示文案，接口返回结构不变。

### 4. 迁移
- `repair_type_rules.office_id` 默认 NULL：现有数据自动成为公司默认，零停机。
- `warehouses.office_id` 从 `community_id` 回填；`repair_type_warehouses` 留一个版本再删。

### 5. 影响面与工作量
后端：规则 CRUD / 自动派单 / stock-options / technicians 四处 + 两条迁移；
后台：报修类型配置弹窗改 Tab、库存页仓库表单加「所属管理处」、派单弹窗按管理处过滤；
员工端：提示文案 + 重新发包（推送 = git / API / 小程序包三件事）。
估计 1.5～2 个工作日，可以拆成「仓库匹配」「规则按管理处」两次上线。
