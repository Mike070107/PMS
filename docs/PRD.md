# 物业管理系统 · 报修管理一期 PRD

> 版本：v0.1 (2026-06-03)
> 项目代号：暂定 `pms-repair`
> 文档定位：本文件既是规划方案，也是一期 PRD。开发开始前以本文件为准；后续迭代沿用同一文件版本号管理。

---

## 1. Context · 为什么做这件事

客户是物业管理服务方，希望搭建自有的物业管理系统。一期聚焦"报修管理"这一最高频、最痛的场景，目标是替代当前微信群+纸单+电话的混乱协作模式，建立**业主报修 → 工单流转 → 维修执行 → 材料消耗 → 采购补货 → 数据沉淀**的完整业务闭环，并为后续物业服务（缴费、公告、投诉、门禁等）打底座。

本系统设计为 **SaaS 多物业公司**形态，开发方提供"代申请微信小程序 + 代运营"增值服务。

### 一期不做的事（明确划入二期/三期）
- 微信支付、维修费在线收款
- 服务号 / 企业微信 通知（仅作扩展点预留）
- 业主缴费、公告、投诉建议、门禁、车位等非维修业务
- 维修工身上的"车载库存"（一期仅总仓 + 小区仓两级）
- 历史报修数据迁移（如有再单独评估）

## 3. 用户角色与核心场景

### 3.1 业主（owner）
- 首次扫二维码 → 微信登录 → 选弄/号/填房号 + 授权手机号 → 等待物业审核
- 通过后扫码直接进入报修表单（自动带出弄/号/房号/电话）
- 历史报修列表，实时查看每张工单状态
- 完工时收到订阅消息，进入工单页验收 + 评分 + 留言

### 3.2 物业办公室（office）
- 浏览器登录后台，电话报修录入页面
- 选弄/号、填房号、填电话、填内容（常用标签快速填）、拖拽上传照片视频、提交
- 也可代业主在小程序代提交（少数线下来人场景）

### 3.3 维修工（technician）
- 员工小程序登录后看"待接单 / 我的工单"
- 系统按规则自动派单，订阅消息推送；可手动接受/请求转单
- 工单详情：地址、报修内容、附件，可一键导航
- 完工录入：工种标签（浮动 chips）+ 维修动作 + 时间 + 材料明细（连库存）+ 费用 + 现场照片视频 → 提交"已完成"
- 缺料场景：填"已用材料 + 缺料清单" → 提交"等待材料"，触发采购申请流转
- 个人 KPI 看板：本月接单数、按时完成率、平均评分

### 3.4 物业经理（manager）
- 审批"等待材料 → 采购申请"
- 查看本物业公司大屏 / 报表
- 处理转单、超期工单告警
- 维修工/办公室人员账号 CRUD、字典维护

### 3.5 采购经理（purchaser）
- 终审采购单 → 选择供应商 → 生成订单
- 供应商档案管理、收货登记、入库（写入总仓 + 调拨到小区仓）
- 比价、对账（一期手工录入）

### 3.6 物业管理员 / 平台管理员（admin / superadmin）
- **物业管理员**：本租户内最高权限，业主审核、配置派单规则、配置二维码、查看所有报表
- **平台管理员**（开发方运营）：新物业公司入驻、租户启停、平台级字典维护

## 5. 业务流程（状态机）

### 5.1 业主入驻
```
未登录 → 微信登录 → 选小区/楼栋/弄号 + 手机号授权 + 房号
        → 提交审核 (pending) → 物业审核 (approved | rejected)
        → approved 后扫码直入报修表单
```
- 反作弊：同 unionid 同房号一年内一次有效审核；rejected 时管理员可填理由，业主小程序展示。

### 5.2 工单状态机
```
created (已提交)
  ↓ 自动派单 or 人工派单
dispatched (已派单)
  ↓ 维修工接单 (可选, 也可省略, 见 5.3)
in_progress (维修中)
  ↓ 完工提交               ↓ 缺料登记
done_pending_review (待业主验收)    waiting_material (等待材料 + 退回工单池)
  ↓ 业主验收 / 48h 超时              ↓ 材料到货：办公室重新派单 or 维修工从池里接回
completed (已完成)               in_progress (回流维修中)

旁路: cancelled (业主撤单, 维修中以前可撤)
旁路: reassigned (转单, 不是终态, 回到 dispatched)
```
- 缺料登记会把 `assignee_id` 置空、工单退回工单池：材料短则半天长则一周，
  不能让维修工的"我的工单"一直挂着干不了的活。等待材料的单在池子里带缺料清单展示，
  可被重新派单（`assign`）或维修工自行认领（`accept` 的 claim 分支）。
- 状态全程留痕到 `work_order_logs`，含操作人、时间、备注。
- 自动派单失败（无可用维修工）→ `created` 状态停在派单池，给物业管理员告警。

### 5.3 自动派单规则
- 输入：报修工种（由报修类型/标签映射）、楼栋/弄/号 → 区域 → 责任片区
- 评分：工种匹配（必选）→ 区域匹配（加分）→ 在手工单数（负分）→ 评分高（加分）
- 输出：得分 TOP 1 的维修工；并列时取最少在手；都无人则进入"待派单池"
- 规则参数全部在租户级配置表，物业管理员可调

### 5.4 采购流程
```
工单 waiting_material → 自动生成"采购申请"草稿（含工单关联）
  → 维修工 / 办公室补全数量、备注 → 提交
  → 物业经理审批 (approve | reject 退回)
  → 采购经理审批 + 选供应商 + 录采购单
  → 供应商到货 → 收货入库（总仓）→ 调拨到对应小区仓
  → 关联工单从 waiting_material 自动回流到 in_progress 并通知维修工
```
- 金额阈值（默认 5000 元）以下，可配"物业经理 → 直采"跳过采购经理。

## 6. 数据模型（关键表）

> 所有表带 `tenant_id`、`created_at`/`updated_at` (timestamptz)、`created_by`/`updated_by`，下表不再赘述。

### 6.1 租户与组织
- `tenants`：物业公司
- `communities`：小区（属于 tenant）
- `buildings`：楼栋（属于 community；含"弄"层级）
- `units`：单元/号
- `houses`：房号
- `qr_codes`：二维码（granularity = community | building，含 token、贴码位置说明）

### 6.2 账号与权限
- `users`：所有用户（wx_openid、wx_unionid、phone、name、role、tenant_id、house_id?、status）
- `user_audits`：业主入驻审核流水
- `roles`：角色（含平台级 superadmin）
- `permissions`：权限点
- `role_permissions`：M2M
- `staff_profiles`：员工档案（工种数组、责任片区数组、是否在岗）

### 6.3 报修与工单
- `repair_requests`：业主侧提交的"原始报修"（保留原始信息）
- `work_orders`：工单本体（指向 request、当前 assignee、status、SLA 计时点、附件、维修动作、费用）
- `work_order_logs`：状态变更与操作流水
- `work_order_materials`：工单关联材料明细（item_id, qty, source_warehouse_id, unit_cost）
- `reviews`：业主验收评价（rating、comment、imgs）
- `tags_repair_common`：常用报修标签（租户级）
- `tags_repair_action`：维修动作标签（按工种关联，租户级）
- `skills`：工种字典

### 6.4 材料与仓库
- `material_categories`：材料分类（树）
- `materials`：材料 SKU（编码、名称、单位、默认成本、图片）
- `warehouses`：仓库（type=central | community）
- `stocks`：(warehouse_id, material_id) 数量 + 安全库存
- `stock_movements`：出入库流水（type=inbound/outbound/transfer/adjust，含来源单据 ref）
- `transfer_orders`：调拨单（总仓 ↔ 小区仓）

### 6.5 采购与供应商
- `suppliers`：供应商档案
- `supplier_materials`：供应商-材料-报价
- `purchase_requests`：采购申请（status 含 draft/manager_review/purchaser_review/approved/rejected/done）
- `purchase_orders`：采购单（供应商、明细、金额、状态）
- `goods_receipts`：收货单（关联采购单、入哪个仓、实际数量）

### 6.6 字典与配置
- `dict_items`：通用字典（type + tenant_id；tenant_id IS NULL 表示平台预置）
- `tenant_configs`：键值配置（派单规则、SLA 阈值、采购金额阈值、订阅消息模板 id 等）

### 6.7 通知
- `notification_templates`：模板（含微信 template_id 映射）
- `notifications`：发送记录（receiver、channel、template、payload、status）
- `subscription_grants`：业主/员工的订阅消息授权次数余量

## 7. 接口设计概要（REST + JWT）

> 全部走 `/api/v1`，前缀 + 多端共用 + RBAC 中间件按权限点鉴权。下面只列代表性接口，完整清单在开发阶段补全。

### 7.1 公共
- `POST /auth/wx-login`：小程序 code 换 session
- `POST /auth/wx-phone`：手机号快速验证
- `POST /auth/admin-login`：后台账号密码登录
- `POST /upload`：通用文件上传（图片/视频 → 对象存储），返回签名 URL

### 7.2 业主端
- `POST /owners/register`：提交入驻
- `GET /owners/me`：个人信息（审核状态）
- `GET /qr/:token`：二维码解析（带出 community/building/unit 默认值 + 审核状态判定）
- `POST /repair-requests`：提交报修
- `GET /repair-requests/mine`：我的报修列表
- `GET /work-orders/:id`：详情（业主只能看自己的）
- `POST /work-orders/:id/review`：验收评价

### 7.3 办公室录入页
- `POST /repair-requests/office`：办公室代提交（自动 OCR 电话搜身份，如无则只录电话与文字）

### 7.4 维修工
- `GET /work-orders?status=dispatched&assignee=me`
- `POST /work-orders/:id/accept`
- `POST /work-orders/:id/transfer-request`
- `POST /work-orders/:id/complete`：含材料明细、附件、费用、维修动作（完工照片选填）
- `POST /work-orders/:id/need-material`：缺料登记 → 转 waiting_material + 退回工单池 + 自动产生采购申请
- `POST /work-orders/:id/missing-materials`：办公室补建 SKU 后更正缺料清单（不新开采购申请）
- `GET /materials/options`：材料选择器数据源（启用中的 SKU，含实物照片、不含成本价）
- `GET /repair-action-suggestions`：维修说明常用话术，按报修类型分组，由历史维修说明归纳排序

### 7.5 物业经理 / 管理员
- `POST /audits/:id/approve` / `reject`
- `POST /work-orders/:id/assign`：手动派单 / 转单
- `GET /dispatch/preview`：派单规则空跑预览
- `POST /tenant-configs/dispatch-rules` 等

### 7.6 采购 / 库存
- `GET /purchase-requests?status=...`
- `POST /purchase-requests/:id/approve`
- `POST /purchase-orders`：采购经理下单
- `POST /goods-receipts`：收货入库
- `POST /transfer-orders`：总仓 → 小区仓调拨
- `GET /stocks?warehouse_id=...&q=...`

### 7.7 报表
- `GET /dashboard/realtime`：实时大屏
- `GET /reports/status-distribution`
- `GET /reports/technician-kpi`
- `GET /reports/top-issues`
- `GET /reports/material-cost`
- 所有报表 `?export=xlsx` 支持导出

## 9. 通知方案细节

### 9.1 消息触发点
| 触发 | 接收者 | 模板字段 |
|---|---|---|
| 报修审核通过/驳回 | 业主 | 结果、备注 |
| 工单已派单 | 维修工 | 工单号、地址、内容摘要 |
| 工单被转单到我 | 维修工 | 工单号、原维修工、转单原因 |
| 工单进入 waiting_material | 物业经理 | 工单号、缺料清单 |
| 采购申请待我审批 | 物业经理 / 采购经理 | 申请号、申请人、金额 |
| 工单完工待验收 | 业主 | 工单号、维修动作摘要、费用 |
| 工单被业主评价 | 维修工 | 评分、留言摘要 |
| SLA 即将超时 | 维修工 + 物业管理员 | 工单号、剩余时长 |

### 9.2 订阅消息授权策略
- 业主端：每次提交报修时默认勾选"接收本次维修进度推送"，覆盖该工单生命周期约 4 次推送
- 员工端：首次进入"我的工单"页弹一次性"长期接收"授权（用一次性订阅消息，通过重复授权累积次数）
- 后端维护 `subscription_grants` 计数器，下推送前先校验余量；不足时降级为站内消息 + 工单页红点

## 10. 安全 / 合规 / 性能

- 所有 token 使用 JWT + Redis 黑名单；移动端短时效（2h）+ refresh token 7d
- 业主只读自己的工单；维修工只读派给自己的；服务端按 `tenant_id` 强隔离，避免越权
- 图片/视频走对象存储 + 签名 URL；后端不存原二进制
- 关键操作（审批、转单、删除）写审计日志 `audit_logs`
- 一期 QPS 预估：单租户日工单峰值 ~200，工程上 1 台 4C8G 应用 + 1 台 4C8G DB 足够
- 备份：DB 每日全量 + WAL；对象存储版本化

## 11. 部署架构

```
微信小程序(业主端) ─┐
微信小程序(员工端) ─┼─► HTTPS (CDN/网关) ─► NestJS API ─► PostgreSQL
管理后台 (Next.js) ─┘                              │      └─► Redis
                                                  └────────► 对象存储 (OSS/COS)
```

- **域名**：`api.{产品域名}` 给小程序 + 后台；`admin.{产品域名}` 后台前端；`cdn.{产品域名}` 对象存储 + CDN
- **微信侧**：在小程序后台配置 request/uploadFile 合法域名；模板消息提前申请到正式 template_id
- **环境分层**：dev（开发机本地 docker-compose）+ staging（云上同生产规格的小机器）+ prod
- **CI/CD**：GitHub Actions → 构建镜像 → 推 ACR → 服务器 docker compose 拉取重启；小程序用 miniprogram-ci 自动上传体验版

## 14. 待澄清 / 二期备忘

1. **派单规则细节**：是否需要"夜间值班工"特殊路径？跨日工单 SLA 怎么算？
2. **维修工评分对 KPI 的权重**：是否影响绩效工资？需要财务接入吗？
3. **多工种维修工**：一人能否兼水电+开锁？派单时如何加权？
4. **缺料采购的紧急通道**：是否允许"先垫付现金现场买"补单？
5. **二维码防伪**：是否要加签名防止打印件被恶意复制？
6. **业主多房号**：一个微信号能否绑多套房（如父母+子女同小区）？
7. **报修隐私**：被维修房屋的照片，业主以外是否对其他业主可见？默认否，但管理员能否查 staff 离职后留痕？
8. **数据导出权限**：哪些角色能导出 xlsx？是否需要水印？
9. **下沉的"非维修"功能**：投诉、咨询是否暂用同一张工单表 type 字段区分，预留 schema 还是完全二期重做？
10. **小程序备案进度依赖**：代申请通常 5-10 个工作日，需要排在 W1 启动。
