# 门禁卡全自动发卡设计稿

> 状态：需求修订后的设计评审稿
> 日期：2026-09-28
> 目标：在任意安装 ACR122U 和“PMS 发卡助手”的 Windows 电脑上发卡；枫桦景苑一期只写卡，二期额外同步门禁数据库并上传控制器；完成后增量同步到 `192.168.1.80` 旧发卡数据库。

## 1. 最终业务流程

1. 打开“门禁发卡”页面。
2. 搜索并选择房号。地址沿用现有格式，例如 `228/5/301` 表示“枫桦景苑二期 / 5号楼 / 301室”。
3. 系统立即展示该基础房号下的全部历史卡片，并自动识别小区期数、楼栋和应走的门禁系统。
4. 默认发 1 张卡，可用 `− / +` 步进按钮调整，范围 1–6 张。
5. 默认授权本楼栋；枫桦景苑二期可添加额外楼栋。枫桦景苑一期不显示无意义的 WG 楼栋权限选择。
6. 点击“开始发卡”，页面提示“请放第 1 张卡”。操作员逐张放卡，完成一张后拿走，再放下一张。
7. 每张卡写入并回读成功后，历史列表立即在顶部新增该卡的 IC 卡号；二期同时显示 WG 卡号和门禁上传状态。
8. 一期卡写入并回读成功即可显示“发卡完成，可以交付”；二期必须等目标门禁控制器上传成功后才可交付。
9. 发卡结果在后台增量同步到 `192.168.1.80` 旧发卡数据库。旧库同步是归档步骤，不阻塞一期卡交付，也不替代二期控制器上传。

## 2. 核心业务规则

### 2.1 房号与历史记录

- 页面搜索使用基础房号，例如 `228/5/301`。
- 旧库中每张卡仍兼容一条独立人员记录，名称格式为 `228/5/301/序号`。
- 同一基础房号的记录合并成一张历史列表，按发卡时间和记录编号倒序，最新卡始终在第一行。
- 列表中的“序号”是该房号的发卡序号，倒序显示，便于一眼判断累计发过多少张。
- 捷顺旧系统编号显示 `HR.Person.NO`，例如 `11251`；它仅是历史编号，不再用于驱动发卡软件。
- IC 卡号来自 `MC.CardInfo.IDNO`，发卡时间来自 `MC.CardInfo.IssueDate`。
- 新系统自己的任务记录立即显示；尚未同步到旧库时，捷顺编号显示“同步中”，同步完成后自动补齐。

### 2.2 一期与二期分流

| 项目 | 卡镜像写入 | IC→WG | 门禁数据库 | 控制器上传 | `.80` 旧库同步 |
|---|---:|---:|---|---|---|
| 枫桦景苑一期 | 是 | 否 | 否 | 否 | 是 |
| 枫桦景苑二期 | 是 | 是 | 按楼栋进入 MjSystem 或 iCCard | 是 | 是 |

期数和楼栋来源于 PMS 房屋主数据，不允许操作员手选“网络版 / 485”，也不根据房号字符串临时猜测。`228/5/301` 只是展示格式，内部仍使用稳定的项目、楼栋和房屋 ID。

### 2.3 卡片要求

- 只接受已经按现有加密规则初始化、并能通过授权验证的 MIFARE Classic 1K 卡。
- 发卡助手必须验证卡型、密钥认证、访问位、格式标记和 UID 唯一性。
- 验证失败时不写任何扇区，统一提示：`非授权加密卡，存在安全风险，无法继续发卡。`
- 永不写 M1 扇区 0 块 0；默认不改写已初始化卡的 sector trailer。
- 每个业务块写完立即回读，整张卡完成后再次全量比对。
- 已发过的 UID 默认拒绝覆盖；挂失、补卡、重发应走独立业务。

## 3. 系统架构

正式方案由 PMS、任意发卡电脑、`.88` 门禁网关和 `.80` 旧库同步服务组成，不再依赖捷顺发卡软件或捷顺发卡 SDK。

```text
任意办公室 Windows 电脑
浏览器 + ACR122U + PMS 发卡助手
             │
             │ HTTPS：任务、状态、读写结果
             ▼
PMS 服务端：权限、状态机、卡号防重、事件、楼栋路由
             │                         │
             │ 二期门禁任务             │ 发卡完成后的归档任务
             ▼                         ▼
192.168.1.88 门禁网关服务              192.168.1.80 旧库同步服务
本机 MjSystem / iCCard MDB             JS0131625 SQL Server
厂商 DLL / COM1 / TCP 控制器           HR.Person / MC.CardInfo
```

### 3.1 为什么不让浏览器直接写卡

- 浏览器不能安全保存 M1 密钥和完整卡镜像。
- 浏览器不能可靠调用 PC/SC 任意扇区读写。
- 网页不得暴露“任意密钥、任意块、任意数据”的通用接口。
- 本地助手可以锁定允许写入的块、执行回读、处理拔卡，并用 Windows DPAPI 保护密钥。

### 3.2 为什么保留 `.88` 本地网关

- 两套 Access 数据库正在 `.88` 的旧门禁程序中使用。
- 部分控制器通过 `.88` 的 COM1/RS232/485 连接，任意发卡电脑无法直接访问。
- MDB 应在 `.88` 本机通过短事务写入，不能从其它电脑经共享目录直接修改。

### 3.3 `.80` 的新定位

`.80` 不再负责实体发卡，只承担兼容旧系统的增量归档：

- 为每张新卡分配旧系统人员 `ID` 和 `NO`。
- 按历史规则保存 `房号/序号`。
- 将 IC 卡号和发卡时间关联到对应人员记录。
- 返回生成的 `HR.Person.NO`，供页面历史列表显示。
- 同步失败时后台重试，不能让操作员重新写实体卡。

正式写入 `MC.CardInfo` 前必须继续核对完整字段、默认值、关联表和约束；旧 PHP 只证明了查询字段和 `HR.Person` 的历史插入方式，不能据此直接拼接不完整的 `CardInfo` SQL。

## 4. 任意电脑发卡设计

### 4.1 PMS 发卡助手

每台需要发卡的 Windows 电脑安装同一套 x86 发卡助手：

- 自动发现 ACR122U，并核对设备型号、驱动和 PC/SC 状态。
- 使用 ACR122U 读取 UID、验证授权、写卡镜像和回读。
- 只领取 PMS 服务端签发的高层发卡任务，不接受浏览器传来的原始卡密钥或任意块数据。
- 密钥与完整镜像只保存在本机 DPAPI 加密存储中。
- 通过出站 HTTPS 领取任务和上报事件，不要求为该电脑开放局域网入站端口。
- 托盘程序显示“发卡器已连接 / 未连接 / 正在发卡”，并提供设备诊断。

### 4.2 工作站绑定

- 首次安装由管理员使用一次性配对码，把电脑注册为一个发卡工作站。
- 页面默认选中当前账号最近使用的工作站，也可以切换到同一办公室的其它在线工作站。
- 点击“开始发卡”后，任务租约绑定到选中的工作站；其它工作站不能领取同一任务。
- 页面明确显示工作站名称和读卡器状态，防止多人同时操作时放错机器。
- 工作站断线后任务保留；恢复在线时从安全阶段续跑。

## 5. 页面设计

页面沿用 PMS 后台设计系统：暖白页面、墨蓝主按钮、青绿色完成状态，红色只用于不可交付或安全阻断。正文和表单不小于 17px，点击目标不小于 44px。

### 5.1 顶部设备状态

一行展示：

- 当前发卡工作站名称。
- ACR122U：已连接、未连接、设备不匹配。
- `.80` 旧库同步：正常、积压、离线。
- 选择二期房号后才展示 `.88` 门禁网关和对应门禁系统状态。

`.80` 旧库离线不阻止实体发卡；二期对应的 `.88` 网关或控制器不可用时，开始前给出明确提醒。是否允许先写卡进入待上传状态，由管理员开关控制，默认不允许。

### 5.2 房号选择区

- 搜索框支持房号、住户姓名和手机号后四位。
- 选中后以大号文字显示 `228/5/301`。
- 辅助文字显示 `枫桦景苑二期 · 5号楼 · 301室`。
- 自动标签显示：`二期`、`MjSystem` 或 `iCCard`；一期显示 `只写卡`。
- 若楼栋映射尚未确认，禁止开始，并说明缺少的映射。

### 5.3 历史卡片列表

选择房号后立即加载，保持在发卡设置下方；发卡过程中不隐藏。

建议列：

| 序号 | 捷顺编号 | IC 卡号 | WG 卡号 | 发卡时间 | 授权楼栋 | 控制器上传 | 旧库同步 |
|---:|---:|---|---|---|---|---|---|
| 6 | 同步中 | `A1B2C3D4` | `12345678` | 刚刚 | 05 | 已上传 | 同步中 |
| 5 | 11251 | `…` | `…` | 2026-09-28 10:20 | 05 | 已上传 | 已完成 |

规则：

- 最新记录置顶，序号倒序。
- 一期的 WG、授权楼栋和控制器列显示 `不适用`，不用空白误导用户。
- 新卡回读成功后立即插入列表，不等待 `.80` 同步完成。
- 二期的每个目标楼栋可展开查看物理门与控制器结果。
- 默认只展开最新几条，其余历史可继续加载。

### 5.4 发卡设置

- 发卡数量：默认 1，`− / +` 步进，范围 1–6。
- 一期：不显示楼栋权限选择。
- 二期：默认楼栋只读选中，可添加额外楼栋；页面只展示逻辑楼栋。
- 系统在后台展开实际门、控制器和时间组，并在“权限预览”里可查看。
- 主按钮：`开始发 1 张卡`，数量变化时同步更新文字。

### 5.5 发卡过程

点击开始后，当前任务成为页面主视觉：

- `正在制作第 2 / 3 张`
- `请放一张已加密初始化的门禁卡`
- 当前阶段：识别卡片、验证授权、写入镜像、回读核对、同步门禁、上传控制器。
- 完成当前卡后提示 `第 2 张已完成，请拿走卡片`；检测到卡片移开后才进入下一张等待状态，防止同一张卡被重复计数。
- 卡片列表实时刷新，最新卡置顶。
- “取消剩余卡片”只取消尚未开始写入的卡，不回滚已经写好的卡。

### 5.6 完成状态

- 一期：最后一张卡回读一致后显示 `发卡完成，可以交付`。
- 二期：最后一张卡的所有目标控制器确认上传后显示 `发卡完成，可以交付`。
- `.80` 仍在同步时，在完成提示下显示非阻断状态：`旧发卡记录同步中，不影响本卡使用。`
- 二期卡已写但控制器未完成时显示阻断提示：`卡片已写入，但门禁权限尚未上传完成，请勿交付。系统将从门禁同步步骤继续。`

## 6. 状态模型

不要用一个状态同时表示写卡、门禁和旧库同步。每张卡拆成三个状态轴。

### 6.1 写卡状态 `cardStatus`

```text
waiting_for_card
reader_detected
uid_read
authorization_verified
writing
readback_verified
card_completed
```

### 6.2 二期门禁状态 `accessStatus`

```text
not_required              # 一期
pending                   # 二期等待处理
access_db_written
controller_uploading
controller_uploaded
waiting_retry
needs_operator
```

### 6.3 `.80` 旧库同步状态 `legacySyncStatus`

```text
pending
person_created
card_record_created
synced
waiting_retry
conflict
```

### 6.4 可交付判定

```text
一期：cardStatus == card_completed
二期：cardStatus == card_completed
   && accessStatus == controller_uploaded
```

`legacySyncStatus` 不参与实体卡可交付判定，但必须在历史记录中持续可见，失败要告警并可重试。

### 6.5 续跑规则

- 写卡前失败，可以从识别卡片重新开始。
- 进入 `writing` 后发生移卡或断电，必须放回同一 UID，先回读判断实际写入程度，不允许盲目整卡重写。
- `readback_verified` 后，二期门禁或 `.80` 同步失败都不能再次写实体卡。
- 门禁数据库和每台控制器分别保存结果，只重试未完成部分。
- `.80` 同步使用卡片任务 ID 和 UID 做幂等，不重复创建人员或卡记录。

## 7. 二期门禁路由

楼栋路由存为管理员确认的版本化配置，不散落在页面代码里。

### 7.1 系统归属

- MjSystem：01、02、03、05、06、07、08、09、10、18、19、20、21、22、23、25、26、32、36 及监控中心。
- iCCard：04、11、12、13、15、16、17、31、33、35、37、40、41、42、45、46、47、48、49、50、51、52、53。

10、36 等尚未证实的物理门映射继续保持“未确认”，不能自动猜测。

### 7.2 权限来源顺序

1. 优先复制同房号现有、有效、已成功上传卡片的物理门权限。
2. 没有可复制卡时，使用管理员确认的逻辑楼栋映射。
3. 两者都没有时停止，提示管理员补充映射。

特殊多门楼栋作为配置保存，例如 01→01+09、19→09+19、25→09+20+25、45 主门+旧门、51 主门+车库门、53 主门+53-1/53-2。

## 8. `.88` 门禁网关

使用 Windows x86 后台服务，以兼容 Jet/ACE、厂商 DLL 和 COM1。

职责：

- 校验两套真实 MDB 的绝对路径、数据库结构指纹和锁状态。
- MjSystem：写 `Employee`，按确定权限写 `MJ_MacPower`。
- iCCard：依次保证 `t_b_Consumer`、`t_b_IDCard`、`t_d_Privilege`。
- 应用层严格检查 WG、人员和门权限重复，不能依赖旧数据库缺失的唯一索引。
- 调用对应厂商上传能力，记录每个控制器的发送与确认结果。
- 数据库独占、串口占用或控制器离线时返回可重试状态，不伪装成功。

数据库写入成功不等于控制器上传成功。只有目标控制器逐台确认后，二期卡才可交付。

## 9. `.80` 旧库同步

在 `.80` 部署只处理旧库同步的 x86 Windows 服务，本机连接 `JS0131625`，不再连接任何实体读卡器。

### 9.1 同步输入

- PMS 发卡任务 ID 和卡片序号。
- 基础房号，例如 `228/5/301`。
- 分配后的房号卡片序号，例如 `6`。
- IC 卡号、发卡时间。
- 二期时附带 WG 卡号和门禁上传摘要，供 PMS 历史审计使用；是否写入旧库取决于旧库真实字段。

### 9.2 同步事务

1. 用任务 ID / UID 查询同步映射，已完成则直接返回原结果。
2. 页面房号与旧库存储格式分开：页面显示 `228/5/301`，查询和写入旧库时使用已核实的 `228/05/301`。在同一事务和房号级锁内查询 `HR.Person.Name`，只匹配 `旧库存储房号/数字序号`，先得到已发数量，再取“现有最大序号与数量的较大值 + 1”。旧 PHP 是模糊匹配记录数后 `+1`；新实现保留连续编号习惯，同时避免相似房号误计数、历史缺号后复用已有序号。
3. 锁定旧 `ID`/`NO` 分配过程，安全生成新的 `HR.Person.ID` 和 `HR.Person.NO`，禁止继续使用旧 PHP 的“查询最大值后直接 +1”并发竞态写法。
4. 写入兼容名称 `基础房号/累计序号`，例如已有 5 张时新用户为 `228/5/301/6`。
5. 按完整数据库约束创建或关联 `MC.CardInfo`，保存 IC 卡号与发卡时间。
6. 提交后回读 Person、CardInfo 及关联，确认一致。
7. 返回累计序号和 `HR.Person.NO`，页面自动把“同步中”替换为真实编号。

如果发现同 UID 已关联到其它房号，进入 `conflict`，禁止覆盖并生成可查询错误编号。

## 10. 服务端数据模型

建议新增以下实体，具体名称按现有 Prisma 命名规范调整。

### `AccessCardIssueBatch`

- 房屋、项目、楼栋 ID 及地址快照
- 数量、默认楼栋、额外楼栋
- 绑定的工作站 ID
- 批次状态、当前卡序号、幂等键
- 操作员、创建/完成时间、最后错误编号

### `AccessCardIssueItem`

- 批次与发卡序号
- `cardStatus`、`accessStatus`、`legacySyncStatus`
- IC 卡号、二期 WG 卡号
- 旧库 Person ID、Person NO、CardInfo ID
- 卡镜像版本摘要，只存 hash，不存镜像正文
- 目标楼栋、门和控制器快照
- 写卡完成、门禁生效、旧库同步时间
- IC 卡号和 WG 卡号唯一约束

### `AccessCardControllerResult`

每张卡、每个目标控制器的数据库写入、上传尝试、确认结果、重试次数和最后错误。

### `AccessCardIssueEvent`

不可变事件日志：任务、卡序号、阶段、工作站/网关、时间、结果、脱敏上下文和错误编号。

### `AccessCardAgent`

代理类型：`issuer`、`access_gateway`、`legacy_sync`；保存机器标识、版本、能力、最近心跳和健康状态。

### `AccessBuildingRoute`

项目期数、逻辑楼栋、目标系统、物理门、控制器、时间组、配置版本、证据来源、确认人和生效时间。

## 11. 接口边界

网页接口：

- 搜索房屋及读取规范化地址。
- 查询基础房号历史卡片，合并 PMS 实时记录和 `.80` 已同步记录并去重。
- 创建发卡批次、订阅实时事件、取消剩余卡、重试门禁或旧库同步。
- 查询工作站、读卡器、门禁网关和旧库同步健康状态。

代理接口：

- 代理心跳、能力与版本上报。
- 按代理类型领取带租约的高层任务。
- 上报阶段开始、完成、可重试失败和终止失败。
- 续租、释放任务和幂等结果查询。

任何接口都不允许传入任意 SQL、任意数据库路径、任意控制器命令、任意 M1 块或原始密钥。

## 12. 安全与审计

- 卡密钥和完整镜像只存在发卡助手本机的 DPAPI 加密存储中。
- Access 密码只存在 `.88` 网关本机的安全存储中。
- SQL 凭据只存在 `.80` 同步服务本机的安全存储中。
- 这些信息不得进入 Git、PMS 数据库、网页、接口正文、截图或普通日志。
- 每个任务包含任务 ID、代理 ID、租约到期、随机数和服务端签名，过期或重复任务拒绝执行。
- 审计记录操作员、房号、UID/WG、镜像版本、权限版本、各阶段结果和错误编号。

## 13. 开发顺序与验收门槛

### 阶段 1：正式页面与模拟全流程

- 按本设计重做当前页面。
- 完成房号搜索、历史列表倒序、默认数量 1、一期/二期自动分流和额外楼栋。
- 建立三状态轴、任务表、事件流和模拟代理。
- 模拟跑通一期、二期、1–6 张、多楼栋、中断续跑和旧库延迟同步。

### 阶段 2：任意电脑发卡助手只读接入

- 完成安装、工作站配对、ACR122U 检测和 PC/SC 诊断。
- 读取授权卡、空白卡和错误密钥卡，证明错误卡零写入。
- 对一次性测试卡采集各阶段差异，确认最终业务块和动态字段。

### 阶段 3：真实卡镜像写入

- 在一次性测试卡上验证单块写入、拔卡、断电和回读失败。
- 逐字节验证写入方向和内容，明确证明扇区 0 块 0 未写。
- 连续多卡时必须等上一张移开后才接受下一张。

### 阶段 4：`.80` 增量同步

- 调研并固定 `MC.CardInfo` 完整写入契约与关联表。
- 使用数据库副本验证编号并发分配、Person/CardInfo 事务、重复 UID 和回读。
- 小范围真实同步后，用旧系统查询确认人员编号、卡号和时间均正确。

### 阶段 5：二期 `.88` 数据库与控制器

- 两套 MDB 分别完成备份和恢复演练。
- 在副本验证查重、同房权限复制、额外楼栋和特殊多门映射。
- 每类连接至少验证一台：MjSystem COM1、MjSystem TCP、iCCard TCP、iCCard 旧 COM1。
- 以现场刷卡成功作为最终证据；数据库写入或 DLL 返回成功都不能代替现场验证。

### 阶段 6：试运行

- 一期先开放真实写卡和旧库同步。
- 二期只开放映射明确、控制器已实测的楼栋。
- 覆盖重复卡、错误卡、中途移卡、MDB 锁、代理离线、控制器离线和断点续跑。
- 观察期保留原有查询和人工恢复能力，不删除旧记录。

## 14. 首批实现边界

首批开发内容：

- 重新设计现有 Web 页面与数据结构。
- 完成服务端任务编排、历史列表聚合和三个模拟代理。
- 建立“任意电脑发卡助手”、`.88` 门禁网关、`.80` 旧库同步三个 Windows x86 工程骨架。
- 先接入真实设备和数据库的只读诊断。
- `cardWrite`、`legacyDbWrite`、`accessDbWrite`、`controllerUpload` 四个危险能力分别由独立功能开关控制，默认关闭。

首批完成标准：页面可用模拟代理完整演示真实操作流程，同时能看到三类真实代理的只读健康状态；不会改动实体卡、旧 SQL 数据库、两套 MDB 或现场控制器。

## 15. 明确停止条件

以下情况必须停止，不能“自动猜测”：

- 卡片不是已授权初始化卡。
- IC/WG 已存在但归属房号不一致。
- 房屋项目期数或二期楼栋映射不明确。
- 写后回读不一致。
- `.80` 旧库结构与已验证契约不一致。
- `.88` 数据库路径、结构指纹或备份状态异常。
- 二期目标控制器没有确认上传成功。

所有错误都显示具体原因和下一步，并提供可在服务端与代理日志中查询的错误编号。
