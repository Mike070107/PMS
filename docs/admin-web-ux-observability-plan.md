# 管理后台体验与可观测性改造计划

## 目标

让办公室、经理和平台运维人员进入页面后，先看见需要处理的事情，再看辅助信息；同时建立可搜索、可追溯、可告警的日志与运行监控闭环。

## 信息优先级原则

1. **要去哪里**：小区、楼栋、房号或公共区域必须独立、完整、醒目。
2. **发生什么**：报修原话、类型、图片放在地址之后，不和编号混在一起。
3. **是否要马上处理**：紧急、即将超时、已超时、等待材料、待复核使用明确且克制的状态色。
4. **谁在负责**：当前维修工、待派/待接状态必须在列表常驻。
5. **已经拖了多久**：停留时间、SLA 截止时间用于排序和催办。
6. **辅助追溯**：单号、来源、创建时间放在次级位置，但仍支持搜索和复制。

## 页面审计与实施顺序

| 优先级 | 页面/区域 | 主要问题 | 改造方向 |
| --- | --- | --- | --- |
| P0 | 工单管理 | 地址藏在报修内容中且为弱色；列表未展示接口已有的报修图片；待派、紧急、超时同时出现时层级混乱 | 独立地址列、报修图片缩略图、问题描述列；把状态/SLA/停留时间组合为处理优先级；待办行突出 |
| P0 | 日志管理 | 只有少量平台敏感操作日志，没有企业登录、重要操作和异常的统一入口 | 新增系统日志页面、权限、筛选、详情、使用与负载概览 |
| P0 | 异常告警 | Web/小程序运行异常没有统一采集，错误只能等用户反馈 | 采集 Web 与两个小程序未捕获异常、API 5xx 和慢请求；聚合去重后通过站内信与微信推送 |
| P1 | 全局框架 | 多数页面重复显示一次页名；卡片标题、操作区、筛选区缺少统一层级 | 页名只由顶栏显示；统一页面工具栏、说明、卡片和表格密度 |
| P1 | 库存/采购/材料 | 指标多但待处理项目不突出；多层 Tab 认知负担高 | 待审、预警、在途优先；基础资料降级；保持独立盘点入口 |
| P1 | 收费/物业费 | 办理、查询、欠费催缴的操作层级混在一起 | 主任务与历史查询分区；欠费、异常账单重点提示 |
| P1 | 房产/业主/用户/角色 | 说明文字过长，筛选与新增按钮位置不统一 | 顶部改为简短业务提示，筛选统一放卡片工具栏，危险操作弱化 |
| P2 | 养护单/报表/二维码/设置 | 页面内部再次套内容容器；部分页面信息密度过高 | 去除重复容器与标题；按“常用/高级”折叠；错误和待办保持显著 |

## 日志与监控范围

- 登录日志：网页账号密码、网页扫码、员工端、业主端；记录成功/失败、账号或用户、来源、时间、IP、设备信息，不记录密码、微信 code、token。
- 重要操作：所有登录后的新增、修改、删除、审批、派单、复核、设置变更；记录方法、路径、操作人、结果和耗时，不保存请求正文中的隐私内容。
- 异常日志：API 5xx、Web 未捕获异常、员工端与业主端小程序未捕获异常。
- 使用情况：页面访问次数、独立用户、各端 API 请求量、热门页面。
- 负载情况：请求量、错误率、平均/最大响应时间、慢请求数、进程内存、服务器内存与负载、数据库连通性和延迟。
- 告警策略：短窗口聚合，达到阈值才产生一次告警；同一指纹冷却一小时，避免微信刷屏。告警写入日志并通知有“日志管理”查看权限的人员。

## 安全与保留策略

- 日志不保存密码、token、验证码、上传内容和完整表单正文。
- 业务日志按租户隔离，平台进入公司视角后只查看目标公司。
- 请求指标保留 30 天，系统日志保留 180 天；清理由定时任务执行。
- 客户端异常上报需登录态，并限制字段长度，防止任意内容写入。
