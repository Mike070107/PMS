## 先看清老库的组织方式，再动手

老库（SQL Server `enetsql.shxwit.com/吴泾物业`，本机 MySQL 是它的迁移副本）
是按**管理处**组织的，但「管理处」在不同片区的含义完全不同，**照着一套规则导会出错**：

| 片区 | 管理处的含义 | 导入方式 |
|---|---|---|
| 枫桦景苑 | 01/09/10 = 一期 / 二期A / 二期B，**地理分区** | 管理处 → 小区，直接映射 |
| 永德片区 | 05 = 全量归档，27~42「分公司私31xx/居21xx/代21xx」= **按房屋性质拆的副本** | 必须按 (弄,号,室) 去重 |

### 永德：同一套房存了 2~3 份

150弄室表有 2441 行，真实门牌只有 **1233** 个 —— 每户在 05 有一份，在
「私31xx（私房）」或「居21xx（居住）」或「代21xx（代管）」再有一份。
照管理处导会把每户建成两三条房产。

**哪一份是现住户**：管理处 05「永德段」最后一笔收款停在 **2005-12-01**，
姓名不同的 999 户里只有 26 户有过缴费记录；分公司那几个码一路收到 2026 年。
所以 **05 是 2004-2005 年的归档，业主姓名要取分公司副本**，
05 只在「这个房号只有 05 有」时兜底（本次 53 户）。

抽查 140弄1号402室：
- 05 → 鲁振山，2004-10 进户，20 张账单，**一次没缴**
- 39（私3117）→ 徐佳莉，2011-01 进户，85 张账单，缴到 2014-10

### 永德：老库没有「永南/永北」字段

拆分依据只能从**车库名**反推 —— `车库名` 表里写着
`09 = 永德永南段1`、`11 = 永德永北段1`、`12 = 永北246号自行车库`、
`13 = 永南140弄19号自行车库`。用 3217 条车位登记的「地址」按车库归票，
得到每个门牌的归属，多数票非常干净（150弄28号 18南/1北，29号 1南/21北），
个别反票是住户租到对面车库，属正常。

规则写在 `legacy-yongde-import.mjs` 的 `YONGDE_RULES`：

| 小区 | 门牌号 |
|---|---|
| 永南140弄 | 1–19（140弄全部） |
| 永南150弄 | 0–28 |
| 永北150弄 | 29–58 |
| 永南5511弄 | 223–234、**316–323** |
| 永北5511弄 | 236–299、324–350 |

⚠️ **5511弄不是一刀切**：316–323 是夹在永北中间的一块永南飞地，别「优化」成一个区间。

归属改起来很便宜（一个号 = `buildings` 表一行的 `community_id`），发现分错直接改，
不用重导房产。

## 联系方式：只在姓名一致时跨副本补

永德三个弄的 93 条联系方式里 **91 条在 05 归档副本上**，选中的现行副本反而是空的。
补捞规则：**两份记录姓名一致才补**（本次补回 56 条，含 20 个手机号）。
姓名不同说明房子换过户，那个号码是上一任业主的，安到现住户名下就是给错人打电话
（37 条属于这种，一律不补）。

## 房产列表的 5000 套天花板（2026-08-27 撞过）

`listHouses` 原来固定 `.limit(5000)`，房产页又是「一次拉全，树和表共用一份数据」。
永德导完总数到 5013，树上显示「全部 (5000)」，13 套房**看不见而且看不出被截断了**。

现在：
- 表格走服务端分页 —— `GET /houses` **传了 `page` 才返回 `{rows,total,page,pageSize}`**，
  不传仍返回数组（房号搜索下拉、前台收费、物业费那几个调用方按数组用，别改它们的口径）。
- 树的角标走 `GET /houses/summary`（按小区/楼栋 GROUP BY，不受分页影响）。
- 两边共用同一套过滤条件（数据范围 + 搜索词），角标和列表才不会对不上。
- 选中分组节点（如「永南永北」）时后端自动展开到它下面的分期，不再是空列表。

**新增大表列表页一律照这个来**，不要再写 `limit(N)` + 前端翻页。
