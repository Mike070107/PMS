# 老系统房产 / 业主档案导入

对应工具：
- [`tools/legacy-fee-import.mjs`](../tools/legacy-fee-import.mjs) —— 枫桦景苑（房产 + 业主 + 收费标准 + 账单）
- [`tools/legacy-yongde-import.mjs`](../tools/legacy-yongde-import.mjs) —— 永德片区（房产 + 业主）

物业费部分见 [fees.md](./fees.md)。房号匹配规则见
[`apps/api/src/common/house-index.ts`](../apps/api/src/common/house-index.ts)，两个导入共用一份。

## 先看清老库的组织方式，再动手

老库（SQL Server `enetsql.shxwit.com/吴泾物业`，本机 MySQL 是它的迁移副本）
是按**管理处**组织的，但「管理处」在不同片区的含义完全不同，**照着一套规则导会出错**：

| 片区 | 管理处的含义 | 导入方式 |
|---|---|---|
| 枫桦景苑 | 01/09/10 = 一期 / 二期A / 二期B，**地理分区** | 管理处 → 小区，直接映射 |
| 永德片区 | 05 = 全量归档，27~42「分公司私31xx/居21xx/代21xx」= **按房屋性质拆的副本** | 必须按 (弄,号,室) 去重 |

### 永德：同一套房存了 2~3 份

150弄室表有 2441 行，真实门牌只有 **1233** 个 —— 每户在 05 有一份，在
「私31xx（私房）」或「居21xx（居住）」或「代21xx（代管）」再有一份。
照管理处导会把每户建成两三条房产。

**哪一份是现住户**：管理处 05「永德段」最后一笔收款停在 **2005-12-01**，
姓名不同的 999 户里只有 26 户有过缴费记录；分公司那几个码一路收到 2026 年。
所以 **05 是 2004-2005 年的归档，业主姓名要取分公司副本**，
05 只在「这个房号只有 05 有」时兜底（本次 53 户）。

抽查 140弄1号402室：
- 05 → 鲁振山，2004-10 进户，20 张账单，**一次没缴**
- 39（私3117）→ 徐佳莉，2011-01 进户，85 张账单，缴到 2014-10

### 永德：老库没有「永南/永北」字段

拆分依据只能从**车库名**反推 —— `车库名` 表里写着
`09 = 永德永南段1`、`11 = 永德永北段1`、`12 = 永北246号自行车库`、
`13 = 永南140弄19号自行车库`。用 3217 条车位登记的「地址」按车库归票，
得到每个门牌的归属，多数票非常干净（150弄28号 18南/1北，29号 1南/21北），
个别反票是住户租到对面车库，属正常。

规则写在 `legacy-yongde-import.mjs` 的 `YONGDE_RULES`：

| 小区 | 门牌号 |
|---|---|
| 永南140弄 | 1–19（140弄全部） |
| 永南150弄 | 0–28 |
| 永北150弄 | 29–58 |
| 永南5511弄 | 223–234、**316–323** |
| 永北5511弄 | 236–299、324–350 |

⚠️ **5511弄不是一刀切**：316–323 是夹在永北中间的一块永南飞地，别「优化」成一个区间。

归属改起来很便宜（一个号 = `buildings` 表一行的 `community_id`），发现分错直接改，
不用重导房产。

## 联系方式：只在姓名一致时跨副本补

永德三个弄的 93 条联系方式里 **91 条在 05 归档副本上**，选中的现行副本反而是空的。
补捞规则：**两份记录姓名一致才补**（本次补回 56 条，含 20 个手机号）。
姓名不同说明房子换过户，那个号码是上一任业主的，安到现住户名下就是给错人打电话
（37 条属于这种，一律不补）。

## 完整地址：「弄」可能是空的（2026-08-31 踩过）

`fullAddress` 原来是 `` `${road}${弄}弄${号}号${室}` `` 直接拼。前面几个片区每行都有弄，
一直没暴露；上海新家临街那 8 间没有弄，拼出来是 **`通海路null弄348甲号商铺`** ——
`null` 三个字母进了地址，维修工和业主看到的都是这个。

现在按房产页 `buildFullAddress` 的同一套规则拼：无弄不写弄，
商铺的「室」本来就是「商铺」二字、不再重复一遍。落库后**用
`select count(*) from houses where full_address like '%null%'` 兜一下底**。

## 目标小区名必须先对上，脚本默认不自动建（2026-08-29 踩过）

`legacy-area-import.mjs` 原来是「PMS 里找不到这个小区名就自动建一个顶层小区」。
当天用户把小区结构重组过（「龙吴路5530弄」改名成「吴泾新村」并挂到管理处底下），
`AREAS` 里的名字没跟着改，脚本**默默建了个游离的顶层「龙吴路5530弄」，
2713 套房全导进了错的地方** —— 房产树上看不出异常，对着数据库才发现。

现在名字对不上会**停下来并列出现有小区**，确实要新建才加 `--create-missing`
（建出来的是顶层小区，之后还得手工挂到管理处下）。

搬回去的代价：`update buildings set community_id=<对的> where community_id=<错的>`
＋删掉误建的小区。房产/业主不用重导（导入按 (小区,弄,号,室) 幂等），
但**如果已经导了物业费，fee_bills / fee_standards 的 community_id 也要一起改**。

### 上海新家：出租房，只导了房源

管理处 44，通海路328弄 16 栋 416 间 + 临街 8 间，共 **424 个单元**，
只有管理处 44 一份，没有归档副本。单元很小（住宅均 21.7 ㎡），
收费项目只有 **02 租金**（55641 条账单，收到 2025-12-30，账期到 202612）——
是出租房，不是产权小区。

两处要注意：
- **临街 8 间的「号」在老库里被填成了字面量「非居住」**，真门牌（348甲/348乙/350甲…）
  塞在「室」里。照搬会在房产树上冒出一个「非居住号」的楼栋，维修工按这个地址找不到门。
  `AREAS.xinjia.normalize()` 把它掰正成「门牌号 = 原来的室、室号 = 商铺」。
- 424 条人员记录是**承租人不是业主**（进户日期统一 2015-01-01，有一条直接叫「空房」），
  且一个电话都没有。用户这次只要「房源信息」，所以 `--skip-owners` 没导，
  要导一条命令的事：去掉 `--skip-owners` 重跑即可（幂等）。

## 房产列表的 5000 套天花板（2026-08-27 撞过）

`listHouses` 原来固定 `.limit(5000)`，房产页又是「一次拉全，树和表共用一份数据」。
永德导完总数到 5013，树上显示「全部 (5000)」，13 套房**看不见而且看不出被截断了**。

现在：
- 表格走服务端分页 —— `GET /houses` **传了 `page` 才返回 `{rows,total,page,pageSize}`**，
  不传仍返回数组（房号搜索下拉、前台收费、物业费那几个调用方按数组用，别改它们的口径）。
- 树的角标走 `GET /houses/summary`（按小区/楼栋 GROUP BY，不受分页影响）。
- 两边共用同一套过滤条件（数据范围 + 搜索词），角标和列表才不会对不上。
- 选中分组节点（如「永南永北」）时后端自动展开到它下面的分期，不再是空列表。

**新增大表列表页一律照这个来**，不要再写 `limit(N)` + 前端翻页。
