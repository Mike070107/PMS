# 多租户用户权限体系设计（RBAC + 数据范围）

> 2026-08-10 与 Mike 逐项确认定稿。实施进度见文末。

## 定位

平台化 SaaS：软件开发企业（平台方）服务多家物业公司（租户），
物业公司内按管理处划分管辖小区。

```
平台（superadmin，tenant_id = null）
 └─ 物业公司（tenants 表，企业租户）
     └─ 物业管理处（management_offices 表，一个管理处管多个小区）
         └─ 小区（communities，顶层小区挂 office_id；下层分期不动）
             └─ 楼栋 → 单元 → 房号
```

## 已确认的设计决策

| 决策点 | 结论 |
|---|---|
| 与现有 `users.role` 的关系 | ~~双轨制~~ → **2026-08-26 合并为一张表**，见文末「业务身份与后台角色合并」 |
| 数据范围绑在哪 | **绑角色**：角色 = 功能权限矩阵 + 数据范围（全公司 / 指定管理处 / 指定小区） |
| 权限动作粒度 | **三档**：查看 / 编辑（含新增修改）/ 删除；无查看权则菜单隐藏、接口 403 |
| 页面结构 | **一页整合**：员工管理升级为「用户管理」（业务身份/工种/在岗 + 后台角色绑定同页） |
| 管理处层落地 | **新建独立表** `management_offices`，顶层小区挂 `office_id`，不动现有小区数据 |
| 分级管理 | **一期简化版**：只有企业超管建角色；有用户管理权的管理处角色只能在自己范围内管人、只能分配范围不超过自己的角色 |
| 数据范围过滤的模块 | 工单管理、房产与业主 + 业主审核、楼栋报修码、工作台统计（材料/库存是仓库维度，暂不过滤） |
| 平台端形态 | **同一后台加「平台管理」菜单组**，仅 superadmin 可见 |
| 平台代操作 | **租户切换**（Salesforce "Login As" 式）：进入公司视角用现成页面操作，顶部常驻提示条 + 一键退出 + 审计日志 |
| 公司级功能限制 | **每公司直接勾选可用页面**（`tenants.enabled_pages`），公司内角色只能在此范围内分配；套餐模板二期再说 |
| superadmin / 企业超管 | 不受权限矩阵限制，直通；每公司内置不可删「企业超级管理员」角色 |

## 数据库改动

| 对象 | 说明 |
|---|---|
| `management_offices` 新表 | tenant_id, name, remark, enabled |
| `communities.office_id` | 新字段，顶层小区 → 管理处，可空 |
| `roles` 新表 | tenant_id, name, remark, data_scope(`all`/`offices`/`communities`), built_in, enabled；(tenant_id, name) 唯一 |
| `role_permissions` 新表 | role_id, page_key, can_view, can_edit, can_delete；(role_id, page_key) 唯一 |
| `role_scopes` 新表 | role_id, office_id(可空), community_id(可空)；选管理处 = 自动含其下全部小区（含后来新增的） |
| `user_roles` 新表 | user_id, role_id 多对多，权限取并集 |
| `tenants.enabled_pages` | jsonb，可用页面 key 数组；null = 全部可用 |
| `platform_logs` 新表 | 平台代操作 / 租户切换审计 |

Schema 变更方式：本次起引入 TypeORM migration（`src/migrations/`），不再依赖 synchronize。

## 鉴权链路

- 后端：`@RequirePermission('page-key', 'view'|'edit'|'delete')` + PermissionsGuard；
  superadmin / 企业超管直通；旧 `@Roles` 在过渡期共存，管理后台接口逐步替换。
- 登录及 `/auth/me` 下发：权限清单（page → 三档布尔）+ 可见小区 id 集合 + 可用页面。
- 数据过滤：范围解析为小区 id 集合后注入查询（工单/房产/审核/楼栋码/工作台统计）。
- 前端：菜单按「查看」过滤，页内编辑/删除按钮按权限显隐；`NAV_GROUPS` 与 `PAGE_TITLES` 合并为单一带 pageKey 的配置。
- 租户切换：superadmin 请求携带目标租户标识，后端校验身份后以该租户上下文执行并记 `platform_logs`。

## 存量兼容

- 现有租户 = 第一家物业公司，`enabled_pages` 默认全部。
- 每公司自动种子「企业超级管理员」内置角色。
- 存量 manager/office 等后台账号自动绑「全功能（兼容）」角色，避免上线即白屏，后续人工收紧。

## 业界参照

- 若依/芋道：菜单权限 + 数据权限（全部/自定义/本部门/本部门及以下/仅本人）双轨模型，租户管理 + 租户套餐。
- 多租户 RBAC：角色带 tenant_id、(tenant_id, name) 唯一、查询层强制注入范围。
- 代操作：two-token / server-side "Login As"，UI 明显标识 + 审计。

## 实现要点（2026-08-10 完成）

- 守卫三件套（`modules/access/`）：`PermissionsGuard`（纯管理端接口）、
  `RolesOrPermissionGuard`（小程序+后台共用接口：业务身份 @Roles 或页面权限任一命中）、
  `PlatformGuard`（仅 superadmin）。范围过滤统一走 `scope.util.ts` 的 `scopeCommunityIds()`。
- 例外约定：**采购审批链（提交经理/经理批/采购批/驳回）、下单、收货、调拨审批
  仍按业务身份 @Roles 把关** —— 这是审批流程语义，换页面权限会让"谁都能替经理批"。
- 兼容种子：`rbac-seed.service.ts` 每次启动幂等执行 —— 每公司种内置「企业超级管理员」；
  存量 manager/office/purchaser 无绑定则自动挂「全功能（兼容）」角色，之后人工收紧。
- 登录准入：owner/technician 默认不能登后台，但绑了后台角色即放行（adminLogin）。
- 租户切换：superadmin 带 `x-acting-tenant-id` 头（jwt.strategy 替换 tenantId），
  进入/退出由 `/platform/tenants/:id/enter|exit` 记 `platform_logs`；
  前端 localStorage `pms.admin.actingTenant` + 顶部橙色提示条。
- 前端权限：`lib/auth.ts` 存 `pms.admin.access`（登录后和每次进后台刷新自一遍 /auth/me），
  `usePagePerm(pageKey)` 控制按钮显隐；菜单唯一配置源在 `AppLayout.tsx` 的 NAV_GROUPS。

## 层级澄清与补齐（2026-08-19 与 Mike 确认后实施）

完整层级：平台公司 → 物业公司(tenants) → 管理处/项目部(management_offices)
→ 小区(communities，含分期 parent_id) → 弄 → 楼栋(buildings) → [单元(units)可选] → 房号(houses)。

已确认的两条「不改」决策：

- **弄不升级为独立表**：弄是 `buildings.lane` 字段（上海式门牌「228弄26号101室」），
  同小区内弄+号组合唯一即可；除非以后要在弄级挂管理属性（弄级报修码/责任人）再拆表。
- **角色、订阅消息不下沉到管理处级**：角色 = 公司级表 + 数据范围限定已能表达
  「各管理处各有各的角色」；订阅消息跟人走，无需挂管理处。

本次补齐的三件事（migration `1787443200000-TenantExpiryAndBusinessScope`）：

| 事项 | 实现 |
|---|---|
| 租户服务有效期 | `tenants.expires_at`（date，含当天，null=永久）。到期/停用后 **jwt.strategy 逐请求拦截全员（含小程序）**，superadmin 不受限（要能进去续期）；adminLogin/员工登录处另给友好文案。平台租户页可设置，列表红/橙标注已到期与 30 天内到期 |
| 前台收费接入数据范围 | `business_transactions.community_id` 新列（按房号→楼栋→小区回填存量）；规则/流水/搜索（房号、车辆、门禁卡按所挂房号的小区 join）全走 `scopeCommunityIds`。受限角色：只见「公司通用 + 范围内小区」规则、只能建/改绑定在范围内小区的规则、办理时校验房号在范围内；规则绑小区后办理时校验适用性 |
| 管理处切换器 | 顶栏 Select（`x-acting-office-id` 头）：`AccessService.applyActingOffice` 把数据范围收窄到该管理处的小区集合（与本人范围求交，**只窄不宽**，无效值静默忽略）；`/auth/me` 下发 `offices` 可切列表；`RolesOrPermissionGuard` 角色路径命中时若视角生效也挂 req.access（否则企业超管在工单共用接口上切了没效果）。全部小区数据页自动生效，无需逐页改造 |

管理处切换器的显隐规则：本人范围覆盖 ≥2 个管理处，或全公司范围且存在管理处。
localStorage key：`pms.admin.actingOffice`；切公司视角、退出登录、角色变更后失效自动清。


## 业务身份与后台角色合并（2026-08-26 与 Mike 确认后实施）

**推翻的是上表第一行的「双轨制」，其余决策不变。**

起因：管理员在后台把某人的角色改成「维修工」，员工端小程序底部照旧是「派单台 / 材料与库存」。
不是 bug 而是双轨制的必然结果 —— tab 显隐读的是 `users.role`（业务身份），
后台改的是另一条轨（页面权限矩阵）。两套东西同名不同义，配的人无从分辨。

| 决策点 | 结论 |
|---|---|
| 合并落点 | `roles.business_role`（varchar，可空）。建角色时选业务身份；null = 纯后台角色，不上小程序 |
| 后台的概念数 | 只剩「角色」一个。用户管理页去掉「业务身份」下拉，只选角色 |
| `users.role` | **保留为派生列**，绑角色时由 `business_role` 同步写入，任何地方都不再手工设。留着它是因为 26 处 `@Roles`、jwt payload、小程序登录跳转、`SELF_SCOPED_ROLES` 的数据隔离都读它，而业主根本不绑角色（`users.role='owner'`） |
| 一人几个身份 | **一个人只能绑一个带 `business_role` 的角色**（否则「他到底是维修工还是经理」无解），可以再叠加若干纯权限角色，权限仍取并集 |
| 一个身份几个角色 | 同公司内一个业务身份只允许一个角色（部分唯一索引 `uq_roles_tenant_business_role`），否则用户管理页会并排出现两个「维修工」 |
| 存量迁移 | `RbacSeedService.ensureIdentityRoles` 幂等补齐：公司里用到的每个身份种一个同名角色（已有同名角色则直接认领，不造第二个），把没有身份角色的人绑上去。**新种的角色权限矩阵故意留空** —— 存量后台权限还挂在「全功能（兼容）」上、权限取并集，所以这一步不改变任何人现有的能看能点 |
| 后台登录准入 | 从「绑没绑角色」改成「**绑的角色里有没有一个可见页面**」。合并后人人都绑角色，再按前者放行等于把后台向全体员工敞开，维修工登进来还会撞上没有菜单的白屏。企业超管（内置角色 / 身份 admin）直通 |
| 审批链 | **不变**：采购提交/经理批/采购批/驳回、下单、收货、调拨审批仍按业务身份 `@Roles` 把关（流程语义），只是身份的来源从手工设变成角色带出来 |

### 权限矩阵扩到两端：角色决定小程序里看到哪几格

合并只是把「他是谁」并进角色；真正让角色有用的是这一步 —— **权限矩阵从「只管网站页面」
扩成两组，同一张 `role_permissions` 表**：

| 组 | key | 谁在读 |
|---|---|---|
| 网站后台 | `dashboard` / `work-orders` / … | 后台菜单过滤、`@RequirePermission` |
| 员工端小程序 | `app:pool` / `app:my-orders` / `app:repair-create` / `app:inventory` / `app:approvals` / `app:messages` | 小程序底部入口、端上按钮显隐 |

每个工种工作流不同，看到的入口就该不同，现在这件事只有一处配置：业务角色。
端上不再有任何硬编码白名单 —— `canSeeTab()` 直接读矩阵，
`utils/session.ts` 的 canDispatch/canEditMaterials 也改读 `app:*`。

配套的几条：

- **接口互认**（`STAFF_APP_PAGE_GRANTS`）：小程序和后台调的是同一批接口，接口上挂的是后台 key。
  勾了 `app:inventory` 就等价于放行 `inventory` / `materials` 的 view/edit，否则「后台勾了、端上还是点不动」。
  `delete` 不走这条 —— 端上没有删除动作，别把后台的删除权顺手放出去。
- **`tenants.enabled_pages` 只裁后台页面**：它是「这家公司买了哪些后台功能」，
  存量租户的名单里当然没有 `app:*`，跟着裁会把整个小程序关掉。
- **后台登录准入只数非 `app:` 的可见页面**：否则「会用小程序 = 能登后台」，
  维修工进来是一屏没有菜单的白板。
- **默认菜单预设**（`DEFAULT_APP_PAGES_BY_IDENTITY`，shared-types 与 api 同源一份）：
  升级种子给身份角色预勾，后台新建角色选类型时也预填 —— 照搬合并前硬编码的那套，
  所以升级当天没有人的入口会多或少。种子只在该角色**一条 `app:` 权限都没有**时写，
  企业超管后来取消掉的格子不会被下次启动加回去。
- tabBar 在 `attached` 里绝不能联网，读的是 `pms.staff.role` + `pms.staff.pages`
  两个缓存，由各页拿到 `/auth/me` 时写入（`rememberAccess`）；**下拉刷新即生效**，不用退出重登。

命名：后台统一叫「业务角色」（菜单、页面标题、用户管理的列名都是它），
不再出现「业务身份」「后台角色」两个说法。角色里那个 `business_role` 字段
在界面上叫「角色类型」—— 它决定工作流（接单 / 派单 / 代报 / 仅后台）。

### 后台这两页长什么样

- **用户管理**：只剩一列「业务角色」（原「业务身份」+「后台角色」两列合并），
  显示角色名，名字与类型不同时才在后面补一行小字标明类型（角色本来就叫「维修工」时
  不再跟一个「维修工」）。筛选下拉列的是**角色管理里真实存在的角色**，
  不是另写一份身份清单 —— 两边对不上时用户会以为筛选漏了人。
- **业务角色 → 编辑**：权限区是两个页签「Web 页面权限」「邻修小程序页面权限」，
  页签标题带已勾数量。每行一个页面，主勾选 = 给不给他这一页；**勾中后就地展开**
  细分档位（Web：查看/编辑/删除；小程序：查看 + 该入口特有的操作，如「接单 / 派单」
  「改材料信息」「审批」）。取消主勾选连带清掉细分档 —— 只清 canView 会在库里
  留下 canEdit 的孤儿记录，下次打开又是一片勾。
  整片三列复选框看上去每格都要决策，实际上绝大多数页面只需要「给 / 不给」，
  所以先是非题、需要细分的人再往下看一层。

### 「勾得出来就必须真的生效」

矩阵里能勾的每一档，端上都要有人消费，否则就是假开关（取消了功能照常，比没这个开关更糟）。
本次一并接上的：

| 档位 | 端上生效点 |
|---|---|
| `app:pool` 的「接单 / 派单」 | 办公室的派单按钮（既有）＋**维修工的接单按钮**（pool 卡片、工单详情） |
| `app:my-orders` 的「处理工单」 | 工单详情的**完工提交、添加用料** |
| `app:approvals` 的「审批」 | 审批页的通过/驳回（在业务身份之上再收紧：同是经理也可只让一部分人批） |
| `app:inventory` 的「改材料信息」 | 材料与库存页的编辑 SKU / 新增（既有） |
| `app:repair-create` | 报修入口（pool 页两个按钮、我的页入口）。**没有单独的操作档** —— 看得到入口就等于能提单，所以默认预设里也不写 `e`，免得库里留一个界面上改不到的位 |
| `app:messages` | 我的页的消息入口 |

每一处被权限收起来的按钮都配了 `.notice` 说明，写清「现在为什么不行 + 去哪儿改 + 改完下拉刷新即可」。

### 上线前踩过的几个坑（多智能体审查发现，均已修）

| 坑 | 现在的做法 |
|---|---|
| **一格权限扩散到整个后台 key** | 曾在守卫里做「`app:inventory` 等价于 `inventory`」的通用映射，结果勾个「报修」就能派单、勾个「采购审批」就能清空库存。改为**在接口自己的 `@RequirePermission` 里显式列 app: key**（见 `inventory.controller`），守卫不再做任何映射 |
| **「一个身份只能一个角色」是错的约束** | 各管理处常要各自的「维修工」（数据范围不同）。唯一索引已删，新建带类型的角色不再 400。真正必须唯一的是**一个人只能绑一个带类型的角色**，在保存用户时校验 |
| **改类型/停用角色会制造孤儿身份** | `users.role` 是绑角色时写的派生列，改角色不会动它 → 人还在派单台被派单，小程序却只剩「我的」。现在**只要还有人绑着，就不许改类型、不许停用**，报错里写清「先去用户管理把这些人改到别的角色」（与 `remove()` 一个口径） |
| **种子每次启动都跑，会回滚管理员的调整** | 加 `tenants.rbac_seeded_at`，**每个租户只补种一次**。否则清空类型、取消入口、停用角色这些操作，重启一次全都变回来，日志里只有一行「seeded」 |
| **按名字认领同名角色 = 一次重启把后台权限发给全体维修工** | 升级前手工建的「维修工」角色可能勾着工单管理的增删改。现在**只认领没有任何后台页面权限的空壳角色**；带权限的不碰，另起「维修工（员工端）」，让企业超管自己取舍 |
| **平台新开的公司当天建不了员工** | 身份角色只由启动种子创建，运行期新建的租户轮不到。现在 `createTenant` / `bootstrapAdmin` 直接调 `RbacSeedService.seedTenant()`，内置角色也补上 `business_role` |
| **一家公司出错，全平台迁移不了** | 种子的租户循环里逐个 try/catch，一家的脏数据不连累其他公司 |
| **角色一停用，绑着它的人再也编辑不了** | 用户管理的角色下拉 = 可分配角色 ∪ 这个人已绑的角色，停用的标成「· 已停用」仍可回显，改个手机号不会被校验挡住 |
| **改类型不重算小程序预设** | 先选「维修工」再改选「保安」，不重算的话这个保安角色留着工单池还能接单。现在只要当前勾选还是上一个类型的原装预设，就跟着换成新类型的 |
| **身份从代报改走，代报授权不回收** | 保安转岗成维修工时一并删掉 `user_report_communities`，免得哪天改回保安时旧授权原地复活 |
| **未读红点点不掉** | 角色没勾「消息中心」时，「我的」页没有消息入口，红点也不再挂 |
