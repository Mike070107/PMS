## 1. 范围与设计依据

在 PMS 中增加独立财务应用。Web 左侧增加「财务记账」入口；员工小程序「更多」增加同名入口。两端仅管理员和指定的叶双账号可访问。项目、流水、发票、报销单不复用物业收费、工单、采购等业务数据。

已核对代码：Web `apps/admin-web/src/components/AppLayout.tsx` 的 NAV_GROUPS 与 `App.tsx` 管理菜单和路由；小程序 `pages/me/me` 的 more 模式承载更多应用；服务端 `modules/access/access.service.ts` 已区分平台管理员和企业管理员。后端 NestJS + TypeORM，Web React + Ant Design，员工端为原生微信小程序。

视觉使用实际 `apps/admin-web/src/theme.ts` 的海军蓝 #31558a、深蓝 #243f69、背景 #eef3f8，沿用现有中文字体回退和 12px 卡片圆角。旧 Web MASTER 中青绿色与现行代码不一致，以已上线品牌及 data-first-ui 技能为准。已阅读两端 MASTER 与 `.claude/skills/data-first-ui/SKILL.md`；未找到独立 ui-ux-pro-max 技能，本轮沿用项目现有规范。

## 3. 信息架构与页面

### 3.1 记账流水（默认首页）

页头：财务记账；右侧「记一笔」。页签：记账流水 / 项目管理 / 报销管理 / 发票台账。优先展示待处理项「待报销」「待补发票」「未归项目」，点击直接筛选，不用大面积图表挤压清单。

筛选：事由或流水号搜索、项目与子项目联动、归属、支付方式、收支、报销状态、日期范围。桌面表格：日期与流水号 / 事由及项目路径 / 归属 / 金额与方向 / 凭证发票 / 报销状态 / 操作。手机号和银行账号不放在流水列表。小屏改金额为视觉锚点的卡片，必要宽表横滑且操作可达。

流水详情保留全部字段、附件与发票、关联报销单、创建人、修改历史。可编辑未报销且未被申请锁定的流水；后补发票有独立入口。已报销流水可补附件与归档信息，但不直接改金额、方向、归属或报销关联；纠错使用保留审计记录的撤销 / 更正流程。

### 3.2 记一笔 / 编辑流水

桌面主区域两列：左侧填写，右侧上传与发票核对；小程序单列全页，分为「消费信息 / 归属项目 / 凭证发票」三节，可跳转，保存按钮不被 tabBar 或安全区遮住。

字段顺序：金额 → 事由（语音）→ 日期 → 归属 → 支付方式 → 方向 → 是否需要报销 → 项目、子项目 → 凭证、发票。金额、事由必填；三组分类均有可见默认或需一次选择。归属和支付方式可记住本人上次成功保存的选择；首次归属不擅自猜公司，首次支付方式暂定微信。方向暂定支出。是否报销首次暂定否，后续记住本人选择，待用户评审。默认日期永远取当天，不能沿用上笔日期。内部流水号、创建人、创建时间自动生成。

从项目详情发起记账时带入项目；普通入口默认无项目。选子项目时只列当前项目下有效子项目；更换项目时清空不匹配的子项目并提示。两个字段都可清空，子项目不能脱离父项目。保存并继续保留分类偏好、清空金额 / 事由 / 附件；不会复制上一笔发票。

金额存定点 DECIMAL 或整数分，禁止浮点求和；输入超过两位小数提示原因，避免静默改变金额。不允许零或负值；方向单独表达。第一期设计为人民币，币种扩展不作为已确认需求。

### 3.3 项目管理

两级结构：项目 → 子项目，不引入无限层级。项目列表显示项目名、子项目数量、流水数量、待报销金额。详情显示项目资料、项目附件、子项目、关联流水。项目汇总明确是否包含子项目（默认包含且不重复累加）。独立显示「未归项目」入口，方便后补。

新建项目只要求名称。新建子项目自动带父项目。说明和附件选填；项目 / 子项目附件各自归属，可在图文说明中插入图片或引用文档。已关联流水的项目以归档代替硬删除；历史关联不丢失。

### 3.4 报销管理

页签：待报销流水 / 报销申请。主按钮「发起报销」。申请页为「填写收款信息 → 选择流水 → 核对提交」三步，填写信息在切换步骤、筛选和失败时保留。

姓名、电话从登录档案预填且可修改；申请时间自动填当前时间。开户行和银行账号优先带入本人上次确认的信息，完整账号仅在有权限的表单中可见。报销事由可编辑，先由所选项目或事由生成建议。筛选项完整提供项目、子项目、归属、报销状态、方向（默认支出，可切收入或全部）、金额范围和流水日期范围。

只有「待报销且未被其他有效申请占用」可勾选。选择已报销 / 无需报销筛选时可查看但不能加入；筛选变化不暗中丢弃已选项，展示「含当前筛选外 N 笔」，支持查看全部已选及清空。底部显示已选笔数、合计与归属分组金额；收支混选分开展示，不未经确认直接净额抵消。提交时二次核验状态、金额版本及权限，通过数据库事务 / 唯一占用约束防止双人重复报销。

建议一个申请对应一个归属，避免不同公司与个人混在同一付款单。跨归属选择时按归属预览拆单结果并保留收款信息；此为设计建议，未作为用户已确认规则。

申请状态建议：待付款 → 已完成；可撤回 / 作废并记录原因。用户没要求多级审批，第一期不自行增加审批链。流水仍只保留用户指定的三种报销状态：无需报销、待报销、已报销；被申请占用时附加「申请中 · 报销单号」，不引入容易混淆的第四种财务状态。

点击「登记已付款」：核对收款人、金额，填写付款日期（当天默认）和付款凭证，服务端完成后流水自动已报销。本系统不自动调用银行付款。第一期暂按整单全额报销设计，部分报销留作后续范围确认。

### 3.5 发票台账与核对

列表：发票号码、开票日期、销售方、购买方、价税合计、识别状态、关联项目 / 子项目 / 流水日期与编号。支持查看原文件和识别结果、手工纠正、跳转流水。暂不把 OCR 等同税务查验真伪。

上传后异步识别：排队 → 识别中 → 待核对 / 可用 / 疑似重复 / 识别失败。展示发票类型、代码（适用时）、号码、开票日期、双方名称与税号、未税金额、税额、含税金额、币种、明细及识别置信度。低置信度字段逐项提醒人工确认，不能凭猜测自动入账。只有用户明确采纳时才回填流水金额 / 日期，不覆盖已填内容。

查重分层：

1. 文件哈希命中：提示相同附件已存在。
2. 归一化票据身份（发票类型、适用的代码与号码等）：明确重复；同一独立账本内跨项目、跨归属、跨报销状态查询。
3. 身份不完整但销方 / 日期 / 金额等相近：疑似重复，列对比结果，请人工核对；不得把相同金额当作必然重复。

重复提示必须带「原项目 > 子项目、流水日期、流水编号、事由、金额、报销状态」，提供「查看原流水」和「移除此张」。确认重复的票据阻止再次作为新的有效报销依据；误判可更正识别字段后重新校验并记录审计。数据库唯一约束处理并发；前端提示不替代后端校验。

一笔流水允许多张发票；一张有效发票首期只绑定一笔有效流水，是否允许跨流水拆分金额尚未要求。多页 PDF 按票据而非文件数量入表。新票后补与首次上传走同样查重。识别失败不阻止保存消费流水，可保留原件进入待核对，但界面不能标成「识别成功 / 无重复」。

## 4. 附件与语音交互

Web：点选、拖拽、聚焦上传区后 Ctrl+V 黏贴截图；图文区可含文字和多个附件。文件逐个显示上传进度、失败原因、重试、取消、移除。图片按完整内容展示；PDF / Office 可预览时预览，其余类型提供下载，不承诺所有格式都能识别或在线打开。具体大小 / 数量上限在实现时与存储和识别服务核对后明示。

小程序：设计为「拍照 / 相册 / 选择文件」，语音输入在事由旁。截图黏贴与桌面拖拽是 Web 交互；不在原生微信界面上摆无法实现的同名按钮。实际文件选择与语音服务可用范围需按现有 SDK 和真机核对。语音按下立即反馈、松开识别、可取消；结果回填可编辑文字，保留键盘输入。

上传文件统一私有存储；下载和预览按账本访问权核验，不能凭永久公开链接访问银行账户或发票。内容类型检测、文件名净化、危险内容不内联执行、图文内容清洗；只有支持的图片 / PDF 等进入识别。识别服务是外部处理方，开发阶段确认供应商及数据处理配置。本轮没有上传真实发票。

## 5. 数据隔离与权限设计

建议采用独立 finance 数据库连接和迁移、独立私有附件空间、独立备份恢复；可共用 API 进程及 PMS 登录验证。财务系统内部有 ledgerId 范围，所有查询、票据查重、报销和附件都受其约束。PMS 企业或管理处切换不得隐式改变账本范围，也不能使别的 PMS 租户管理员自动获得此账本。

访问判据：当前账号有效，且为该账本所属组织的管理员，或为已核实绑定的叶双 userId；平台管理员按明确账本范围授权处理。叶双可能有多条岗位档案，必须解析到唯一登录用户，不使用姓名字符串动态放行。开发前只读核对账号身份，不把真实手机号写入设计文档。

服务端返回 financeAccess；Web 菜单、路由和小程序入口复用。未加载权限时默认隐藏，直达页面、API、批量导出、发票识别任务结果、文件下载均拒绝未授权访问。普通角色矩阵不能给其他员工绕过专属白名单。退出或撤权后清理财务页面缓存，不在通用离线缓存中保留财务敏感内容。

建议实体：

| 实体 | 核心责任 |
|---|---|
| ledger / ledger_member | 账本与授权身份映射，仅存外部 PMS userId，不跨库外键 |
| project | 两级项目结构、父级、归档状态 |
| entry | 流水号、业务日期、归属、事由、金额、方式、收支、是否报销、项目关联、版本 |
| attachment / attachment_link | 私有文件元数据、哈希、项目 / 流水 / 发票 / 报销用途关联 |
| invoice / invoice_line | 票据身份、OCR 原始结果及校对结果、查重状态、关联流水；明细单列 |
| recognition_job | 识别任务、重试次数、结果版本及失败原因 |
| reimbursement / reimbursement_item | 收款信息快照、申请状态、流水金额快照、有效占用 |
| reimbursement_payment | 付款确认时间、金额、凭证、操作者 |
| audit_event / user_preference | 变更审计、默认选项、本人常用收款信息 |

流水是否已报销由有效付款关系派生；不让前端提交任意状态。申请中的关键字段冻结或先撤回再编辑。所有写请求防重复提交，关键记录支持乐观锁；失败返回具体字段 / 规则和追踪号。

## 6. 异常状态与验收范围

- 空列表给「记一笔 / 新建项目」；加载、无权限、失败、上传超时、识别失败都独立提示并可恢复。
- 表单失败不清空；切换页面有未保存提示；银行账号使用文本输入保留前导零，详情脱敏。
- 必验权限矩阵：指定叶双账号 / 同名其他人 / 管理员 / 普通员工 / 未登录 / 已撤权；菜单、深链、API、附件各自测试。
- 必验新建与后补：无项目、仅项目、带子项目、换项目、无发票、后补发票、多票、跨项目重复、并发重复。
- 必验金额：0、负数、超过两位小数、超上限、千分位展示、精确求和、收支分组。
- 必验报销：默认支出、全部筛选项、筛选外已选保留、两人同时申请同笔、撤回释放、付款幂等、状态一致、已付款关键字段不可直接修改。
- 必验设备：Web 桌面 / 360px / 1024px；员工端真实手机、系统字体放大、长事由 / 项目名称、满屏附件，保存按钮可达。
- 本轮预览为虚构示例，只演示页面交互；未验证真实 OCR、语音、上传、权限或付款。

## 7. 实施顺序（页面评审后）

### 8.2 总体流程与后台同步

QQ 邮箱 → 邮件增量采集 → 提取附件/受支持的下载链接 → 文件去重 → 票据解析与识别 → 票据身份去重 → 发票收件箱 → 自动关联或人工匹配 → 更新流水的票据状态。

建议在服务器运行独立收票 worker，首期每 5 分钟轮询一次，后台可改，可手动「立即同步」；这是产品建议频率，实施时通过 QQ 实际连接与限流测试确定。不依赖用户开着 PMS 页面或本机程序。首次同步范围已由用户确认为最近 7 天，以首次实际同步时刻向前 7 天的邮件收件时间为准，后续只处理新增；可按日期补历史，不把“仅未读邮件”当作增量条件。

连接设置：邮箱地址、授权码、采集文件夹（收件箱和用户选择的规则归档文件夹）、首次同步日期、自动同步开关、轮询间隔；「测试连接」「立即同步」「暂停」「更换授权码」。状态显示最近尝试时间、最近成功时间、本次新增/重复/待人工/失败数、下一次检查时间。授权失效、超时、文件无法解析分别提示具体原因，不把“同步请求已接受”当作全部成功。

服务端同步要求：

- 只读打开文件夹并使用不标记已读的抓取方式；不发送、移动、删除邮件，不改变已读状态。授权码本身可能具备更广权限，应用通过代码约束只读。
- 每邮箱、每文件夹记录 UIDVALIDITY 与 UID 游标；UIDVALIDITY 改变时重新建立基线并依靠幂等去重。Message-ID 辅助查重，不能假设始终存在或唯一。
- 同步游标推进前，先可靠保存已发现邮件任务；失败任务保留重试记录，不能跳过失败 UID 后永远漏票。重启、重跑、邮件移动、跨邮箱转发都不重复生成有效票据。
- 文件哈希用于原件去重；归一化票据身份用于 PDF/OFD/XML 同票不同格式的合并。多个文件版本保留在同一票据下；跨邮件来源保留关联，不因同票重复收取就再挂一遍流水。
- 附件支持 PDF/OFD/XML、图片和受限 ZIP 解包，限制大小、解包层级和总解压体积。优先解析结构化内容或 PDF 文本，无法可靠解析再 OCR；不是每张票都调用大模型。
- 邮件只含下载链接时，按支持的平台适配；防止内网地址/危险重定向访问。验证码、登录要求、过期链接进入「需手动下载」，网页打印件不能冒充正式发票原件。
- 凭据加密保存，密钥独立管理，界面仅回显脱敏状态；留空不改，更换需重新测试。不要把授权码粘进聊天、日志或 Git。只有管理员可管理连接；叶双继续拥有收票处理权限。
- 收件箱先属于被授权的财务工作空间；购买方税号明确时分派至对应主体，无归属的进入该空间待分派队列。不同租户不能共享邮箱或收件箱。原始邮件头与必要正文私有保存，不将整封邮件默认发送给 OCR 服务。

### 8.3 页面：发票中心

现有「发票台账」提升为「发票中心」，内部三个入口：收件箱 / 已归档发票 / 邮箱连接。避免在财务顶层不断增加页签。

收件箱页头突出「待处理 N 张」，旁边显示邮箱连接状态与最近成功时间；右上角「立即同步」「邮箱连接」。页签筛选为待匹配、已关联、重复票、识别异常、已丢弃；支持按归属、金额、开票日期、来源邮箱筛选。

桌面以“左侧票据清单 + 右侧处理面板”呈现：

- 清单每项突出金额与销售方，辅助显示购买方、开票日期、邮件来源和状态。
- 处理面板上半部分展示原件预览与识别字段，下半部分展示候选流水。
- 候选卡展示流水事由、金额、日期、项目/子项目、归属、报销状态和匹配依据。例如“金额一致、购买方税号一致、订单号一致”，不只给不可解释的 AI 分数。
- 主操作「关联所选流水」；次操作「搜索其他流水」「暂不处理」「丢弃」。无流水时提供「按发票新建记账草稿」，用户确认实际是否付款、日期和支付方式后才能生成资金流水，不凭发票自动认定已支出。
- 已关联票显示是系统还是人工关联、时间和目标流水；未过账且允许修改时可撤销关联重新选择，已报销/已过账的采用更正流程并保留历史。

小程序：更多 → 财务记账 → 发票中心 → 待处理清单 → 发票详情 → 候选流水选择。金额和操作优先；预览与识别字段可展开，不把桌面双栏压成小字。邮箱连接管理优先在 Web 操作，手机显示同步状态与异常原因。

### 8.4 自动匹配与人工处理规则

自动采集默认开启与否由连接配置决定；自动关联单独开关。建议初始启用保守规则，模糊结果始终人工核对。

| 情形 | 建议动作 |
|---|---|
| 已识别的同一发票已关联流水 | 合并新来源和文件版本，显示原流水；不建立第二个消费或报销依据 |
| 同主体、同币种、金额一致、可信订单/付款参考号一致，且只有一个可关联流水、识别字段已可靠确认 | 自动关联并写规则版本和依据；只补票据关系，不改金额、项目或报销状态 |
| 仅金额相同，或金额+时间相近 | 推荐候选，不自动关联；开票日期不等于付款日期 |
| 多笔候选、多个同额消费、同一天多张票 | 人工选流水；候选不可按列表首项自动决定 |
| 抬头/税号冲突、币种冲突、已占用、识别不确定 | 明确显示冲突；先更正识别或选择正确主体，不能强行自动匹配 |
| 没有匹配流水 | 暂存待认领；人工搜索或新建草稿；后续新增流水再触发匹配 |
| 一票多次付款、多票合并付款、红字票、退款、个人垫付跨主体 | 进入人工核对/分摊流程；不按总金额做简单一对一绑定 |

金额比较使用精确分值，时间窗口只影响候选排序。付款人和购买方不一定相同，个人垫付公司的消费是正常场景，归属按业务主体确认，不能仅凭收件人或付款账户归属判断。

人工搜索可查事由、流水号、项目、子项目、归属、收支类型、金额区间和流水日期。选中后显示两侧对比；后端提交事务重新检查版本、授权范围、重复身份和可分摊余额。

“丢弃”定义为从本系统待处理队列移除，默认可恢复；原因可选「非发票」「与本账本无关」「重复材料」「其他」。已关联/已报销的有效发票不直接丢弃，应先按权限解除或更正业务关系。丢弃不删除 QQ 邮件、不删除已有流水，也不代表发票在税务系统作废。保留文件指纹及处置记录，下次扫描不反复出现；一封邮件多张票时按票处理，不连带丢弃其他票。

### 8.5 为专业财务软件预留的基础模型

本节是长期方向建议；它更新第一版“单账本内归属标签”和“一票一流水”的简化设计，但不擅自认定已启用多个独立主体账套。正式开发前统一确认采用此长期模型，避免先建硬限制再重做。

1. **工作空间 → 核算主体 → 账套 → 会计期间。** OsirisList、普睿斯各自拥有主体档案与账套；个人资金独立账户/个人账本，不混入公司总账。操作仍保留用户熟悉的三项归属 Radio，内部映射真实主体。只有授权用户可汇总查看多主体；不直接把跨公司相加当作合并财务报表。
2. **发票、费用、资金流水、报销申请、会计凭证分别建模。** 发票证明票据事项，支付证明资金变动，报销付款用于结清垫付款；不能上传发票再新增一次费用、报销付款又新增一次费用，导致成本被重复统计。
3. **发票可先独立存在。** invoice 不依赖非空 entryId，新增 allocation 表记录关联对象、分摊金额、币种、操作者、时间和更正记录。第一期 UI 可先支持一对一和多票一单，数据结构允许后续一票多单；有效分摊不能超可用金额，并发时也不能超占。
4. **账户和支付方式分开。** 微信/支付宝/对公/现金是方式；实际微信账户、银行卡、现金账户分别有身份、币种、归属和余额。内部账户互转不计营业收入或费用，借款/还款等不按普通收支直接解释为利润。
5. **普通录入继续用收入/支出。** 专业会计模块另设科目表与复式凭证，不把记账页改回要求用户判断会计借贷。用户确认的“收入/支出”是日常资金表达，不代表利润表的收入费用确认口径。
6. **已过账不可覆盖修改。** 草稿可编辑，审核/过账后通过冲销或更正凭证，保留来源单据；期间关闭后限制变更，重新打开期间需授权及审计。
7. **数据独立可迁出。** 独立财务库、迁移、附件、备份恢复和 API 作为推荐基线；PMS 只是一个入口，登录身份通过映射接入，未来可增加独立域名和其他业务系统入口，不依赖 PMS 物业业务实体。

新增建议实体：mail_connection、mail_folder_cursor、mail_message、mail_attachment、invoice_source、invoice_inbox_item、invoice_match_candidate、invoice_allocation、sync_run、sync_job；专业阶段新增 legal_entity、accounting_book、fiscal_period、financial_account、accounting_subject、journal_entry、journal_line、reconciliation、expense、settlement。名称为设计建议，不代表本轮已建表。

### 8.6 分阶段产品路线

| 阶段 | 交付能力 | 完成判断 |
|---|---|---|
| A 收支与票据闭环 | 项目/子项目、收入支出、凭证、报销、QQ 增量收票、人工匹配/丢弃、去重和审计 | 从邮箱原件一路追溯到消费流水和报销付款；无重复收票或重复计费 |

| C 专业会计 | 科目表、凭证模板、审核过账、总账明细账、试算平衡、期间结账、资产负债表/利润表/现金流量表 | 凭证平衡、明细与总账一致、报表可追溯；企业会计口径需实施时明确 |

### 8.7 邮箱同步与关联的必要验收

- 新邮件、已读邮件、规则移入文件夹、转发邮件、历史补拉均能覆盖；原邮件已读标记和所在文件夹不变。
- 重启、网络中断、游标失效、任务重跑、并发扫描不重入；失败邮件能重试且无遗漏。
- 同票 PDF/OFD/XML、同附件多次转发、一封多票、跨主体同金额各自按正确层级合并或区分。
- 自动匹配测试包含唯一参考号命中、仅金额相同、同额多候选、抬头冲突、日期延迟、币种不同；模糊结果不得自动挂单。
- 人工关联、撤销、丢弃恢复、新增流水后重新推荐均有审计；已丢弃条目不会每轮同步重新出现。
- 凭据失效有真实错误和最近成功时间；授权码、原邮件正文不进入日志；跨账本下载或访问返回拒绝。
- 一票多单分摊并发不能超额；归档、作废、更正后仍可还原票据、费用、付款和会计凭证之间的关系。

当前未进行 QQ 邮箱连接实测、真实发票识别或第三方项目运行；需要在实施阶段以测试邮箱和已授权样本验证。微信文章正文尚未取得，作为明确的参考缺口保留。
