## 已经建好、只差业主端入口（最划算，优先做）

### 我的车辆 / 我的门禁卡
- 现状：`parking_vehicle`、`access_card` 两张表已有车牌、卡号、**有效期**、状态；
  `business_transaction` / `business_rule` 记录办理流水与计价规则。
- 缺的只是权限与入口：`/business/*` 的 `@Roles` 现在只开给
  ADMIN / MANAGER / OFFICE / SUPERADMIN，业主看不到自己名下的车和卡。
- 价值：业主打给物业最多的两个问题就是「我车位什么时候到期」「这张卡还能不能用」。
  做成只读列表 + 到期提醒即可，几乎不用写新业务逻辑。

## 真正的空白，物业刚需

### 小区公告
- 现状：**完全没有**，无实体无接口。
- 价值：停水停电、电梯保养、疫苗接种。这是业主**每天会打开小程序**的理由 ——
  报修不是（一年可能就用几次）。物业现在多半发业主群，刷两条就没人看见。
- 依赖：消息中心（一期已做）—— 公告要能推送才有意义。

### 投诉建议 / 表扬
- 报修解决「东西坏了」，但「楼上漏水扰民」「保洁没打扫」没有工单载体，
  业主只能打电话吵。可复用报修那套工单流，换个类型即可。

### 访客通行码
- 业主生成一次性二维码给来访亲友，保安扫码放行。
- 已有完整的 `qr_code` 生成链路（楼栋码 / `getUnlimitedWxaCode`），改造成本比看上去低。

## 报修做深（不是新模块，属于一期核心的增强）

> 2026-08-21 两项均已实现：随手拍地址识别（`POST /repair-requests/parse-address`，
> 解析逻辑在 `apps/api/src/modules/repairs/repair-address.util.ts`）；

### 随手拍：描述里自动识别报修地址（2026-08-21 Mike 提出）
- 诉求：语音/文字里出现「一期 24号302」「二期6号」时自动定位地址；
  说到房号填到 houseId，只说到楼栋填到 buildingId（**公区单不挂房号**，口径同现有 scopeIds）。
- 可行性：**不需要 AI**，库内字典精确匹配即可 ——
  communities 已有「分组→分期」两层且每个分期已算出主弄（一期→198弄，见
  properties.service `communityPhases` 的主弄逻辑），buildings 有 lane+buildingNo，houses 有 roomNo。
- 做法：正则抽「(N期)?(X弄)?(Y号)(Z室)?」候选 → 按报修人租户的楼栋/房号字典精确匹配 →
  命中即预填，**展示出来允许改**（全局规则：默认值必须能改，提交时关联 id 跟着变）。
  没识别到就维持现状（默认本人房屋）。「侯队报一期24号大门关不上」→ 地址 198弄24号。
- 不做：从文本里抽联系人姓名（「侯队」）。登录人姓名电话系统已知，直接用；
  文本抽名字误判率高、收益低。

### 报修类型纠错自学习（同日提出）
- 现状：类型关键词**后台已可配**（工单页「报修类型规则」，带真实使用次数排序），
  小程序 classifyRepairType 已在用 —— 「大门」加进「公共设施相关」关键词今天就生效。
- 缺口：工单 repairType 创建后**没有改的入口**，管理员无处纠正。
- 做法（半自动，可解释可撤销）：
  1. 后台工单详情加「改类型」，同时落 correction 记录（原判定、命中词、纠正后类型、描述原文）；
  2. 纠正时从描述抽候选词，一键「以后『大门』归到公共设施相关」→ 写进目标类型关键词、
     从原类型移除；管理员在关键词页能看到并删除学到的词；
  3. 攒够纠正记录后，第二步再考虑「同一词被纠正 N 次自动迁移」的全自动版。
- 现有打分里长词命中得分更高，「大门」天然能压过「门锁」的「门」，不用改算法。

## 建议单独立项，不要顺手做

### 物业费缴纳
听起来最该有，但它是系统级工程：账单生成、滞纳金规则、微信支付商户号、
对账、退款、发票。**做一半比不做更糟** —— 业主付了钱查不到账，投诉量会直接翻倍。
等前面几项稳定后单独立项。
