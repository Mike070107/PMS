description: 记一条待办进收件箱（不带参数=按顺序把待处理做完）
---

收件箱 = `docs/bug-inbox.md`。

> 这个命令原来叫 `/bug`。Claude Code 自己有个同名内置命令（向 Anthropic 反馈），
> 内置的优先，于是打 `/bug` 只会弹官方反馈框、这份提示词根本不会执行
> （2026-09-01 实测）。所以改名 `/inbox`，别再叫回去。

输入：$ARGUMENTS

## 有输入：只记一条，不要动手

把它追加到「## 待处理」段末尾，然后停下。

- 格式 `- [ ] <今天日期> | <端> | <现象> | <复现路径>`；端从描述里判断（owner/staff/web/api），判断不出写 `?`。
- 描述太简略时补一句你猜的入口页面（写在复现路径里，加「?」表示未确认）。
- **只写这一条，不要顺手去修、不要读代码、不要跑构建。** 写完回一句「已记录，第 N 条待处理」。
- 例外：内容是在回答我刚问你的问题（「要做 X」这种），那是决定不是待办，直接执行。

## 没有输入：按顺序把待处理清空

1. 读「## 待处理」，先列出还有几条、分别是什么，说明打算按什么顺序做（默认从上往下）。
2. 一条一条做，每条都走完整条链路：改 → 本地校验（typecheck / build / 单测）→ 提交（只 `git add` 明确路径）。
3. 每做完一条就把那行改成 `[x]` 挪到「## 已修复」，附提交号；不要攒到最后一起改。
4. 做不了的（信息不足、要我拍板、和别的会话冲突）跳过，最后统一说明为什么，别卡住整条队列。
5. 全部走完后按 `/ship` 收尾：推送 + 部署受影响的目标 + 打标记。
