# 生产发布：计时、精确复用与失败重试

正式入口不变：`./deploy/publish-production.ps1 -Target auto`。

## 已定位的问题

- 原门禁在档案/车位回归前构建新版 Web，正式打包又无条件构建一次。
- Web 版本取当前分钟，导致同源码重试的编译输入变化，无法安全复用。
- 打包/上传中断后，已完成构建和制品未建立可校验复用凭据。
- Windows PowerShell 5.1 会把 pnpm/tar 的普通 stderr 包装成 NativeCommandError；遇到 Stop 偏好时，退出码0也可能误报失败，造成反复重跑。现在区分原生提示与真实脚本错误，并以原生命令退出码判断失败，专门回归覆盖三种情况。
- 原入口没有完整的分段计时。不能把每次人工准备、排查和验证的耗时全部归因于部署脚本。
- 本批优化前正式入口实测约4分钟；两次依赖安装各不足1秒，因此没有删除安装或必要门禁来制造提速。

## 现在如何工作

1. 冻结已推送的 main 提交，先统一设置正式 Web 编译环境、CI 和该提交时间对应的稳定版本。
2. 保留原有按影响范围选择的回归。其输入哈希还绑定 pnpm 版本、相关发布工具及编译环境。
3. 同一个 Web 构建供门禁与打包使用；API 也支持同输入构建复用。每次复用前核对所有 dist 输出文件的 SHA256、增删文件和符号链接。
4. 缓存身份包含目标、完整提交、源码/锁文件/工具输入、Node/pnpm、平台/架构、打包模式、VITE/NODE_OPTIONS 等环境；Node 预加载脚本字节变化同样失效。环境值只参与哈希，不写进凭据。
5. 制品首次登记读取 tar 内真实 release.json，核对目标、提交、源码指纹、版本和完整元数据。续跑还核对 tar 的 SHA256，并恢复这一制品的预期身份，不给旧包冒充新版本重新盖章。
6. 编译失败不写成功凭据；损坏凭据、输出/包缺失或篡改均不能作为成功证据。上传前源码保护、生产原生依赖预检、在线版本/制品校验和 deployed 标签仍保留。

## 重试和排查

- 中断后在同一干净、已推送提交执行原入口即可；不要修改包或手动伪造凭据。已部署且标记成功的目标直接跳过，未完成目标重新核对门禁、构建及制品身份后继续。
- 更换提交、相关源码/依赖/发布工具、编译环境或模式，必须重新验证；这不是缓存故障。
- 凭据和阶段计时位于 `artifacts/release-checks`。`publish-*-timings.json` 包含总耗时及各正式阶段；`commands-*-timings.json` 记录实际构建/回归子命令。打包内部安装、部署依赖和压缩也输出 `[release-phase]`。
- 失败的正式发布也保存已执行阶段与失败状态。清理凭据仅意味着下次重做，不构成绕过门禁。

回归：`node --test deploy/release-check.test.mjs deploy/neighbor-production.test.mjs deploy/release-cache.test.mjs`。
